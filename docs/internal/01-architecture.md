# Hoserva — Architecture

---

## 1. Stack

| Layer | Technology | Rationale |
|---|---|---|
| Base OS | Debian stable — Debian 13 (trixie) for 1.0 (Q4) | Hardware support, stability, fully CLI-manageable |
| Pooling | mergerfs — Debian 13 package, version range pinned (Q7) | Arbitrary disk sizes, no rebuild on growth; one mount per share (Q12) |
| Parity | SnapRAID — Debian 13 package, version range pinned (Q7) | One or two parity disks for `n` data disks (Q19) |
| Disk health | smartmontools | SMART attributes, self-tests |
| Disk control | hdparm / sdparm | Spindown control |
| File sharing | Samba (+ Avahi), nfs-kernel-server | SMB / NFS; Avahi for discovery and Time Machine |
| Backend | Go | Single static binary, systemd service, good at orchestrating subprocesses |
| State | SQLite (WAL mode), pure-Go driver `modernc.org/sqlite` (Q6) | Single-file, no server, transactional, no CGO |
| Frontend | React SPA built with Vite (Q8); coss ui components on Base UI + Tailwind CSS v4 (D15) | Static assets embedded in the Go binary; no Node runtime in production; components vendored into the repo, no runtime design-system dependency |
| API | REST + SSE over Unix socket and TCP; spec-first OpenAPI 3.1 with a generated server and clients (D18, Q63) | Consumed by the web UI, the CLI and scripts alike — nothing the UI does is unavailable to them |
| Container runtime | Docker Engine + Compose plugin | **Prerequisite**, not shipped by the `.deb` |
| Virtualization | libvirt + QEMU/KVM — Debian 13 packages, `go-libvirt` (no cgo) | Same engine Unraid's own VM Manager runs on; PCI/USB passthrough via VFIO (doc 14, Q58) |
| Remote backup transport | rclone (optional) | Every remote backup destination (doc 10, Q41) |
| Backup encryption | age (`filippo.io/age`) | Archives encrypted before they leave the box (doc 10, Q80) |
| UPS | NUT (optional) | Clean shutdown on battery (Q77) |

### Why Go

- Single static binary — trivial `.deb` packaging, no runtime dependency hell
- Strong subprocess handling, which is 80% of what this backend does
- Good SQLite and systemd story
- Cross-compiles for arm64, which matters for the many homelab boxes that aren't x86 — built from day one, supported once the public beta covers it (Q5)

### Why a static SPA rather than SSR — and why not Next.js

The backend serves the UI. Shipping a Node runtime onto a NAS appliance to server-render a dashboard is unjustifiable overhead. Static assets plus a REST API keeps production to one process.

Next.js static export was the original choice and does not fit: `output: 'export'` requires every dynamic route segment to be known at build time, and this UI's core routes (`/storage/disks/[id]`, `/shares/[name]`, `/apps/[name]`) only exist at runtime. Static export also discards everything Next adds. A Vite-built SPA with a client-side router is the plain version of the same architecture (Q8); the Go server returns `index.html` for any non-API path.

## 2. The source-of-truth model

This is the single most important architectural decision, and the one that determines whether Hoserva is usable by the kind of person who buys it.

### The problem

Tools that generate config files fail when users hand-edit those files. The UI overwrites the edit, the user loses work and trust, and the tool gets a reputation for being something you must not touch. It is a common failure mode of appliance-style NAS software.

### The model

```
                    ┌──────────────┐
   web UI  ────┐    │              │
                ├──▶ │  REST API   │ ──▶ SQLite (source of truth)
   CLI     ────┘    │              │             │
                    └──────────────┘             │
                                                 ▼
                                        config generator
                                                 │
            ┌────────────────────────────────────┼────────────────────┐
            ▼                  ▼                 ▼                    ▼
    /etc/snapraid.conf   mergerfs mount   /etc/samba/smb.conf   /etc/exports
                            (systemd)
```

**SQLite is authoritative.** Every generated file carries a header:

```
# ============================================================
#  Generated by Hoserva — DO NOT EDIT
#  Changes will be overwritten on the next configuration apply.
#  Edit via the web UI or:  hoserva <command>
#  Generated: 2026-09-14T10:33:12Z   Config revision: 47
# ============================================================
```

### Drift detection

On every apply, and on a periodic timer, the backend hashes each generated file and compares against the hash recorded at generation time. A mismatch means someone hand-edited it.

Response is **not** to silently overwrite. The UI raises a warning:

> `/etc/samba/smb.conf` has been modified outside Hoserva. [View diff] [Discard my changes and regenerate] [Keep the file and stop managing it]

The third option matters. A user who genuinely needs a Samba feature Hoserva doesn't expose should be able to take ownership of that file without fighting the tool. Hoserva marks it unmanaged, stops regenerating it, and shows a persistent banner.

### Escape hatches by design

- **Per-file opt-out**, as above
- **Config include directories**: generated Samba config ends with `include = /etc/hoserva/smb.custom.conf` — user-owned, never touched, applied after the generated block
- **SnapRAID extra options** passthrough field in the UI, for flags Hoserva doesn't model

The principle: *Hoserva should be the easy path, never the only path.*

**On a host that is already in use**, the first apply finds files Hoserva didn't write — an existing `smb.conf`, `/etc/exports`, fstab mounts. They are never overwritten: onboarding offers each for import into the database or to be left unmanaged (Q76).

## 3. CLI

Ships with the backend. Speaks to the same API over the Unix socket, so it works with no network and no auth token on a local root shell.

```
hoserva status                          # overall health, one screen
hoserva pool status                     # per-disk breakdown
hoserva disk list
hoserva disk add /dev/sdX --role data [--format xfs]
hoserva disk remove /dev/sdX --evacuate
hoserva disk replace --failed /dev/sdX --new /dev/sdY
hoserva disk upgrade --old /dev/sdX --new /dev/sdY   # larger disk, old one kept until verified (Q71)
hoserva disk external mount|eject <label>          # disks outside the array (Q72)
hoserva array stop|start                # maintenance mode (Q70)

hoserva pool rebalance [--dry-run]      # doc 09 §3
hoserva disk resume <job-id>            # resume a checkpointed relocation (Q29)

hoserva sync [--dry-run] [--force]      # SnapRAID sync through the threshold guard; dry-run prints the diff
hoserva scrub [--percent 8] [--all-blocks]   # --all-blocks scrubs blocks of every age, not only those older than 10 days (doc 02 §2)
hoserva fix --disk 3                    # one disk, back to its state at the last sync
hoserva fix --confirm --path /mnt/user/docs/tax.pdf   # one file; every other change since the last sync stays (doc 02 §2)
hoserva mover run                       # doc 09 §2

hoserva share list
hoserva share create media --smb --guest=no --cache=then-move

hoserva app list

hoserva stack edit <name> --file F [--dry-run]   # validate, store and mark manually edited; nothing restarts
hoserva stack start <name>              # docker compose up --detach as a job, so an edit takes effect

hoserva vm list
hoserva vm create --name winvm --vcpus 4 --mem 8G --disk 100G --iso win11.iso

hoserva migrate scan --flash-backup <zip> [--unverified-layout] [--full-checksums]   # Unraid pre-flight (doc 05, Q25)
hoserva migrate scan --flash-device <device> [--unverified-layout] [--full-checksums] # the same, read from the attached Unraid stick
hoserva migrate status                          # the session's phase and the report's verdict
hoserva migrate report [-o <file>]              # the go / no-go report as a document
hoserva migrate templates [<name>]               # the scan's template conversion preview: the list with counts, or one template's preview
hoserva migrate forget                          # delete the session and the stored zip
hoserva migrate import [--role <serial>=<role> ...] [--cache-partition <by-id>:<partuuid>] --yes   # adopt the data disks read-only, writing nothing to them (doc 05 §4 steps 14-16)
hoserva migrate verify                          # compare the adopted disks with the scan's baseline before parity (doc 05 §4 step 16); exits non-zero on a mismatch
hoserva migrate initialize-parity [--confirm '<string>']   # step 17, the point of no return: format the former parity and cache disks and queue the initial sync; without --confirm it prints what it would erase and formats nothing (doc 05 §4)
hoserva migrate undo-import --yes               # take back an import that is still before its point of no return
hoserva migrate containers                      # Phase D (doc 05 §4 steps 19-20): list what the scan offers and what has been created
hoserva migrate containers create [<name>...] [--acknowledge <name>]... --yes   # create stopped stacks from templates and Compose Manager projects, after printing their Compose and warnings
hoserva migrate containers start <name>         # start one created stack as a job and wait for it
hoserva migrate containers check <name>         # whether the started stack's bind mounts under /mnt/user or /mnt/cache exist and are not empty
hoserva migrate containers confirm <name> [--accept-failed-check]   # confirm the started stack sees its data, which offers the next
hoserva migrate checklist [ack <item>]          # what is left after the migration; ack records user_scripts or restore_drill, the two items nothing else records
hoserva migrate vm-scan                         # Unraid VM definitions from the adopted pool (doc 14 §5)
hoserva migrate vm-import <domain-name>

hoserva config export -o hoserva-config.tar.zst   # archive format per doc 10 §1
hoserva config import hoserva-config.tar.zst      # in-place, or bare-metal on a fresh install
hoserva backup run [config|appdata] [--destination <name>]
hoserva backup list
hoserva logs [--job <id>] [--follow]
hoserva doctor                          # prerequisite + sanity checks
hoserva update [--check]                # Hoserva itself, from its own release index (Q67)

hoserva user reset-password <name>      # root only, over the Unix socket (Q78)
```

`--json` on every command, for scripting.

`hoserva doctor` deserves emphasis: it checks Docker presence and version, mergerfs/SnapRAID versions, mount state, parity freshness, SMART status, free space, and permission sanity, and prints a plain-language report. It is the first thing to ask a user for in a bug report.

### Subsystem abstraction — critical for testability

Every subsystem that touches the real system sits behind an interface, named by its package (`disk.Provider`, `parity.Engine`):

```go
// package disk
type Provider interface {
    List(ctx context.Context) ([]Disk, error)
    SMART(ctx context.Context, dev string, mode SMARTPollMode) (SMARTReport, error) // mode: respect standby (smartctl -n standby) or force a wake
    Spindown(ctx context.Context, dev string) error
    Format(ctx context.Context, dev string, fs FilesystemType) error
}

// package parity
type Engine interface {
    Sync(ctx context.Context, opts SyncOpts) (<-chan Progress, error)
    Diff(ctx context.Context) (DiffReport, error)
    Scrub(ctx context.Context, pct, olderThanDays int) (<-chan Progress, error)
    Status(ctx context.Context) (ParityStatus, error)
    Fix(ctx context.Context, opts FixOpts) (<-chan Progress, error)
    Check(ctx context.Context, opts CheckOpts) (<-chan Progress, error)
}
```

This is not architecture astronautics — it is what makes development possible without a NAS on the desk. See doc 06.

### Job system

Every long-running operation (sync, scrub, rebuild, mover, disk format, container pull) is a job:

- Persisted in SQLite, survives a daemon restart (marked `interrupted` on restart, **never automatically resumed**)
- **Resumable job types** (mover, rebalance, evacuation, share relocation, and the data- and parity-disk upgrades) persist a checkpoint and continue from it — not from zero — when the user resumes them, or for the mover at its next scheduled run. Sync, scrub and fix are re-run, not resumed (Q29). A data-disk upgrade resumes only as its state machine allows (doc 02 §4).
- Progress streamed over SSE to the UI
- Cancellable where the underlying tool supports it, and honestly marked non-cancellable where it doesn't
- Full stdout/stderr captured to compressed files and downloadable, kept 90 days (Q74)
- **Mutually exclusive classes**, enforced by the job scheduler rather than trusted to the UI:

  | Class | Jobs | Excludes |
  |---|---|---|
  | **Parity** | sync, scrub, fix, check | Parity, Array-write, Topology |
  | **Array-write** | rebalance, evacuation, share relocation, mover, VM disk relocation | Parity, Topology, other Array-write on the same disks |
  | **Topology** | disk format, add/remove/replace disk, pool remount, migration scan, migration import, migration verify, migration parity | Everything in the three storage classes |
  | **Service** | appdata backup, config backup, container update | Other Service jobs on the same container (a config backup: another config backup) |
  | **VM** | VM start, stop, create, delete, snapshot, clone, migration-import (doc 14 §2, Q56) | Other VM jobs on the same VM |

  A migration scan and a migration verify only read, but they are Topology jobs so that no storage job runs beside them. They are the Topology jobs that do not take the pre-topology config backup, since they change nothing that backup protects and repeated runs must not use up the retention real changes rely on.

  A migration import (doc 05 §4 steps 14-16) is a Topology job that adopts the Unraid data disks read-only and takes the pre-topology config backup like the others. From its adoption until the point of no return has finished the migration is *unfinished* (`ArrayStore.MigrationUnfinished`): *pending* (`array_settings.migration_pending`) from the adoption until the point of no return records the formatted parity and cache disks, then *initializing* (the record of the former disks, `array_settings.migration_recorded`, is kept) until its last step drops it. The scheduler admits no Parity, Array-write or Topology job while it is unfinished but the import's own retry, the migration verify, which only reads, and the migration parity job (the point of no return, doc 05 §4 step 17), and refuses the rest with `migration_in_progress` (409). A migration parity job takes the pre-topology config backup like the other real changes; it is not resumable, and an interrupted one is finished by running it again. A scan is among the refused, so the baseline the verify step compares against is not replaced, and so is forgetting the session. The question is asked of the array's own record before any job is admitted, and a failure to answer refuses the job. Nothing else is gated: until the point of no return an Unraid import has no `snapraid.conf`, so there is no parity engine and the maintenance chain has nothing to sync. The initial sync the migration parity job queues is an ordinary sync job, admitted once the migration is finished.

  The nightly maintenance chain (Q30) runs its steps in sequence and holds each class in turn.
- **Every sync goes through the threshold guard** (doc 02 §2), whatever triggered it — schedule, disk add, evacuation, or a manual click.
- **Maintenance mode** (`hoserva array stop`, Q70) refuses new jobs, stops resumable jobs at their next checkpoint and marks the rest interrupted.

### Database schema and schema migrations (D16, Q60)

The SQLite database is the system's definition (D4): a schema migration that loses data loses the user's shares, users or disk mapping. Three rules follow from that.

**One central schema.** `internal/store/schema/schema.sql` is the only hand-edited description of the database, and every table in it is declared `STRICT` — required by the migration tool below. Typed Go query code is generated from it with sqlc (`internal/store/queries/*.sql` in, `internal/store/db/` out, committed like `api/gen/`). Nothing else declares a table.

**Schema migrations are generated and immutable.** `make db-migration NAME=<slug>` runs `sqlite-migrate generate` (Q60), which diffs the schema the existing migrations produce against `schema.sql` and writes the next file to `internal/store/migrations/` — including the complete rebuild sequence for a change plain `ALTER TABLE` can't express (a column type or constraint change), generated automatically rather than hand-written. A change that would drop a table or column is refused unless `--allow-destructive` confirms it was intended. After a migration is written, the file is never edited; a mistake is corrected by changing `schema.sql` and generating another migration — committed and reviewed as a generated artifact, the same discipline as `api/gen/`.

- Each migration file carries a checksum header over its own body. `make db-check` (`sqlite-migrate check`) fails if a file's body no longer matches its header, or on drift: replaying every migration into an empty database must produce exactly `schema.sql`.
- That checksum is a self-consistency check, not a content-vetting gate — nothing inspects what statements a migration file contains beyond it. The safety property a runtime allow-list used to enforce now rests on process alone: a migration file is committed only as `sqlite-migrate generate`'s literal output, never hand-edited.
- The daemon refuses to start if the database has an applied migration its own embedded `migrations/` doesn't include — `sqlite-migrate`'s own pending-migration check, not bespoke Hoserva code (Q60).

**Every schema migration is data-safe.**

- `sqlite-migrate generate` never emits a drop, a column type change or any other structural rewrite of a table without `--allow-destructive`, and even then always by rebuild-and-copy, never by discarding data with nothing standing in for it.
- Moving data needs knowledge no schema diff has (`size_mb` becoming `size_bytes`). Only in that case is there a **data transform** — the single exception to generation: a Go function in `internal/store/transforms/`, bound to a migration's checksum and tested against every fixture database. `sqlite-migrate`'s own library has no hook to run one inside its own apply step (Q60), so Hoserva's own apply loop below runs a migration's bound transform immediately after that migration's SQL, inside the same transaction. Every change a generated migration can carry safely on its own gets no transform.
- The order is expand (add the new structure), transform (copy and convert), then contract (remove the old structure) — the contract in a later release than the transform, never the same one. Data with no new home is never dropped.

**Applying schema migrations at startup.** Hoserva's own thin apply loop (package `store`) is built on `sqlite-migrate`'s exported library pieces (`LoadDir`, `PendingMigrations`, `Checksum`, `Snapshot`) rather than its `Runner.Apply`, because `Apply` runs its whole batch as one closed function with no hook for a transform to run inside it (Q60):

1. The daemon loads the embedded `migrations/` and calls `PendingMigrations` against the database; a database with an applied migration missing from that set is refused outright — an older binary never runs against a newer schema.
2. Before the first pending migration, it writes a consistent snapshot with `sqlite-migrate`'s own `Snapshot` function to `/var/lib/hoserva/backups/pre-migration/` (doc 10 §1's consistency rule), keeping the snapshots of the last three upgrades. This retention is Hoserva's own `Snapshot`/`PruneSnapshots` package-local logic in `internal/store`, not `sqlitemigrate.Runner`'s `SnapshotDir`/`RetainSnapshots` fields — those belong to the library's own `Runner.Apply`, which this apply loop doesn't call (Q60).
3. All pending migrations run in one transaction on a single pinned connection, in order: each migration's SQL executes, then any transform bound to its checksum runs immediately after and before the next migration's SQL. Foreign-key enforcement is suspended for that transaction and `PRAGMA foreign_key_check` runs before commit — SQLite's documented procedure for table rebuilds — followed by `PRAGMA integrity_check`, and the applied checksum is recorded in the same bookkeeping table `sqlite-migrate`'s own CLI reads, so `sqlite-migrate status`/`check`/`verify` keep working against the resulting database.
4. Any failure rolls the transaction back, and the daemon exits with the failing migration and the snapshot path in its log and systemd status. There are no down migrations; returning to an older release means restoring that release's snapshot.

## 5. API

REST over two transports:

- **Unix socket** at `/run/hoserva/hoserva.sock` — root and the `hoserva` group, no auth token required, used by the local CLI. The group is created empty; **membership is root-equivalent**, exactly like the `docker` group, and the docs say so (Q44).
- **TCP** on `:8008`, **TLS-only** — session auth for the web UI, personal API tokens (Q43) for scripts and the remote CLI. A plain-HTTP request on that port gets a short response pointing to `https://` (Q9). Ports 80/443 are never claimed; reverse-proxy containers need them.

Same handlers, different auth middleware.

Server-Sent Events at `/api/v1/events` for live data: job progress, disk state changes, container state changes, new notifications. Not WebSockets — the traffic is one-directional and SSE reconnects for free.

### The contract (D18, Q63)

**`api/openapi.yaml` is the API, written by hand; everything else is generated from it** — the same arrangement as the database (D16): one hand-edited source, generated code around it.

- **Every capability is an operation.** Anything the web UI or the CLI can do, every destructive action and its confirmation included, is a documented operation in the spec. There are no internal or undocumented endpoints, so a script or an integration can do everything the UI can.
- **The server implements generated interfaces.** Go server interfaces, request validation and routing are generated from the spec, and the handlers in `internal/api/` implement them. A missing handler, or one whose types don't match the spec, is a compile error, and no route exists that the spec doesn't declare.
- **Clients are generated.** The web UI calls the API only through the generated TypeScript client, and the CLI only through the generated Go client. Neither builds URLs or request bodies by hand.
- **Authorization is declared per operation.** Each operation names the role it requires in `x-hoserva-role` (`admin` or `viewer`; share-only users have no API access, Q27). A lint rule rejects an operation without one, middleware enforces it, and API tokens are scoped the same way (Q43).
- **Live data is part of the contract.** Every SSE event type on `/api/v1/events` is a schema in the spec, typed in the generated clients. ogen alone cannot generate a server or client for this one operation (it supports only SSE clients, and refuses generation entirely once any operation in the spec has a server-side `text/event-stream` response, Q63); `make gen` still generates the `Event` schema's Go types and a Go SSE-frame reader for it, using ogen's `jschemagen` tool against `api/event-schema-root.yaml`, so the CLI reads this stream only through generated code like every other operation.
- **Reads can be shaped for pages.** A data-dense page such as the dashboard gets a purpose-built read operation rather than a dozen calls. It is a documented operation like any other, and it keeps computation in the backend.
- **Why not GraphQL.** The API is mostly guarded, job-producing actions rather than flexible reads; per-operation authorization on a root daemon is simpler to get right than field-level authorization and query-cost limits; and server, clients, mock server and reference docs all generate from one OpenAPI file. Unraid's official API is GraphQL; Hoserva's migrator reads Unraid's files, not its API, so nothing depends on matching it.

### Versioning

`/api/v1/`. The API is public by definition (the CLI uses it), so it needs to be treated as an interface with compatibility guarantees from the first release. Breaking changes are caught mechanically: CI compares `api/openapi.yaml` with the last release's spec, and a breaking change fails unless it lands in a new API version (Q63).

## 6. Boot medium and disk layout

Unraid boots from USB and runs from RAM, writing to the stick only on config change. A normal Debian install cannot do this — it would destroy a USB stick within months of journal and log writes.

Hoserva needs a real boot device.

**Recommended:** a small dedicated SATA SSD (128 GB is ample, ~€20). The NVMe stays fully available as cache, and the boot device can be swapped without touching cache data.

**Acceptable:** partition the NVMe — ~60 GB root, remainder as cache partition. Works cleanly, costs some cache capacity.

*How it is created.* In the Debian installer's partitioner, make the root partition (~60 GB) and then a second partition from the remaining space — type "Linux filesystem", no filesystem, no mount point, not swap — and leave it unused. Hoserva never creates or resizes that partition: it never writes the partition table of the disk it runs from. Phase 4's installer can create it itself (#100).

*What Hoserva does with it.* `GET /disks` lists the boot disk's spare partitions as cache candidates (`cachePartitions`): a partition qualifies when it is on the boot disk, typed Linux data, has no filesystem or swap signature in udev's cache, is not mounted, not named in `/etc/fstab` or a systemd mount or swap unit, is held open by nothing, and has a by-id link and a PARTUUID. Listing never opens the device; if any of those sources cannot be read, nothing is listed. Such a partition can be assigned the **cache** role and nothing else — never data or parity, and never adopted. When it is, the array-create job re-resolves the partition's identity and probes it blank immediately before `mkfs`, then formats exactly that partition through its `/dev/disk/by-id/…-partN` path. The root, `/boot`, the EFI partition, swap, the rest of the partition table and the whole boot disk are never written. The cache mounts at `/mnt/cache` by filesystem UUID like any other cache, and `hoserva doctor`'s free-space check keeps reporting the root filesystem only. Because the boot copy of the content file and a copy on the cache share one disk, the cache gets no content file of its own and counts as the same device (Q18, doc 02 §2).

**Not supported:** USB stick as the OS device. The installer should actively warn if the target device is removable.

### Layout principle

```
Boot device     ──  Debian root, /etc/hoserva, /var/lib/hoserva (DB, metrics DB, job logs, stacks, catalog, first SnapRAID content file, local backups — Q74)
NVMe (cache)    ──  /mnt/cache                  (appdata, write cache)
Parity disks    ──  /mnt/parity1[, /mnt/parity2] (SnapRAID parity, XFS, not in the pool — Q19, Q20)
Data disks      ──  /mnt/disk1..N               (individual filesystems, XFS by default)
Pool            ──  /mnt/user                   (mergerfs catch-all over /mnt/disk*)
Shares          ──  /mnt/user/<share>           (one mergerfs mount per share, branches by cache mode — Q12)
Mover target    ──  /run/hoserva/array/<share>  (array-only mergerfs mount per share, internal)
External disks  ──  /mnt/disks/<label>          (outside the pool and parity, mounted on request — Q72)
```

Paths deliberately mirror Unraid (decision D10). A migrated Compose file referencing `/mnt/user/media` works unchanged.

**The OS is disposable.** A reinstall plus `hoserva config import hoserva-config.tar.zst` must fully restore the system. This has to be true from the first release, and it has to be tested as a routine case (doc 06), not assumed.

**Debian keeps itself patched.** Security updates install unattended; a reboot is always the user's action, and it runs the clean shutdown sequence (Q68, Q70).

## 7. Security

A NAS holds everything a person owns digitally and increasingly gets exposed to the internet by users who shouldn't expose it. Defaults matter more than features here.

- **No default credentials.** First boot forces admin account creation before anything else is reachable.
- **HTTPS only** on `:8008`, with a self-signed cert generated on first boot, plus one-click Let's Encrypt via DNS-01 for those with a domain (Q9).
- **LAN-only by default**: the listener accepts connections only from loopback, RFC 1918, link-local, IPv6 ULA and CGNAT `100.64.0.0/10` (Tailscale) source addresses — a source filter rather than an address binding, so it survives DHCP changes. One explicit, warned-about toggle accepts all sources (Q10); switching it back off also closes the open connections from addresses the filter no longer allows, rather than leaving them usable until they go idle.
- **Secrets at rest** (SMTP passwords, notification tokens, API keys, ACME keys) are encrypted in the DB with a machine key in `/etc/hoserva/secret.key` (root, `0600`, and owned by root — not merely readable only by it), generated once at first start and never silently regenerated afterward — a missing or mismatched key is a fatal startup error, not a fresh key that can decrypt nothing already encrypted under the real one (Q28, whose own entry ends with the recovery procedure that error names). Backups re-encrypt secrets under a user-set backup passphrase (Q28, doc 10 §1).
- **No telemetry.** Hoserva's own update check (Q67), the catalog refresh (Q65) and the daily container update check (Q81) are the only outbound requests it makes on its own, besides renewing a Let's Encrypt certificate the admin has set up (Q9); none of the three checks sends anything beyond a plain HTTP request, and each can be disabled (Q49).
- **TOTP available from v1**, and prompted for (not silently optional) when the UI is reachable from a non-private address.
- **Rate limiting and lockout** on login, per account and per source address: 5 free attempts, then a backoff that doubles with each further failure up to a one-hour ceiling. No response signal — status, error code, or timing — distinguishes an unknown username from a real one with a wrong password: each gets its own lockout budget (a real account's own, or a per-username bucket for a name that isn't one), reached at the same threshold either way, and a login failure runs the same bounded argon2id-shaped work regardless of which subject admitted it. This holds under ordinary load; the unknown-username and source-address budgets each live in a capped, evictable table (10,000 subjects each), so a sustained flood large enough to fill and evict from the unknown-username table can lift an unknown username's own lockout early, whereas a real account's lockout is never capped or evicted, and a new name arriving while every entry in a full table is locked out is answered with a short wait (`429`) that a real account's never gets — an accepted residual, not a defect. Every loopback source address (the whole `127.0.0.0/8` range and `::1`) also shares one address subject rather than each getting its own, so a local unprivileged user can exhaust that shared budget and back off every loopback caller — including a browser on the host itself — for the same window; this is accepted too: a local user can already exhaust the host in other ways, and the Unix socket account-recovery path below is never rate-limited.
- **Account lockout is an accepted LAN denial-of-service surface.** The backoff above has no ceiling on who can trigger it: any LAN client that knows or guesses the admin's username can keep backing off the real admin's own account indefinitely, the same way a forgetful admin locks themself out. This is accepted rather than tightened further; the root-only recovery path below also clears a lockout, not only reset credentials, so the account stays recoverable without waiting the backoff out (Q78).
- **Account recovery is root-only.** A forgotten admin password or lost TOTP is reset with `hoserva user reset-password` over the Unix socket; a locked-out account is cleared with `hoserva user unlock <name>`. All three recovery commands are accepted only when the peer credential is **uid 0 specifically** — the `hoserva` group and the daemon's own uid (Q44's dev-run note) are not enough — audit-logged and announced through every notification channel (Q78).
- **The ups control socket (`/run/hoserva/ups-control.sock`) is `root:nut 0660`, not `hoserva`-group.** upsmon splits into a privileged parent, which alone ever runs SHUTDOWNCMD, and an unprivileged child (Debian's own `RUN_AS_USER` default, the `nut` account) that runs NOTIFYCMD and, for a network UPS, the upsd protocol client parsing whatever a remote NUT server sends back — code Hoserva doesn't own reachable from the network. That child needs the ups control socket, but `hoserva` group membership is root-equivalent (it also admits `hoserva.sock`, whose API can format disks), so `nut` never joins it. The socket instead names the `nut` group directly — `nut` is always a member of its own group, so this needs no packaging or admin step — and `authorizeUnixPeer`'s Q44 admission rule is checked per socket against the group each one names, never against `hoservaGroup` for both (#340).
- **A credential change revokes every other session of that account** — when TOTP is confirmed, every session already issued to that account except the one that made the change is revoked immediately (setting or resetting a password and root disabling TOTP must revoke the account's sessions the same way, and a password change or a root reset or disable must revoke its API tokens too — not yet built, #744); sessions last 30 days without re-authentication, and a stolen cookie or token from before the change must not survive until its own expiry (Q84).
- **The API runs as root** because it partitions disks and mounts filesystems. This is unavoidable, and therefore the attack surface must stay small: no arbitrary command execution endpoint, no user-supplied paths passed unsanitised to shell, template `<ExtraParams>` parsed rather than interpolated into a command line.
- **The optional browser terminal is off by default** and gated behind a confirmation that explains it is root shell access.
- **Container privilege warnings**: templates requesting `privileged: true`, host networking, the host PID namespace, the host cgroup namespace, device cgroup rules, added capabilities, disabled or replaced confinement (`apparmor:unconfined`, `seccomp:unconfined`, `label:disable`, `no-new-privileges:false`), extra groups, or Docker socket mounts are flagged in the install flow with a plain-language explanation. One-click catalogs make it easy to install these without seeing what they grant.
- **The catalog is signed.** A catalog archive is used only after its signature verifies against the catalog key compiled into `hoservad`, and an archive older than the current one is rejected (Q65). That key is separate from the release-signing key, and each compiled-in key verifies only its own kind of file. The private half is the `HOSERVA_CATALOG_SIGNING_KEY` secret on the catalog repository (Q39) and is held nowhere else; the public half is `signing-key.pub.pem` at that repository's root, and its CI checks the secret against it before signing. A leaked catalog key can get templates signed but never a Hoserva release.
- **Catalog refresh is conditional and user-controlled.** One conditional request per check (for the archive and, after a `200`, its signature; a signature that fails verification makes the check fetch the pair once more before reporting the failure), with the same signature and serial checks on every path: a background interval the user sets (off, hourly, every 6 hours, every 12 hours, daily by default, jittered), a check when the catalog is read through the API and the last check is older than 15 minutes (on by default; served from the on-disk copy, never waiting on the network, announced on `/api/v1/events`), and a manual check that always works and always reports a failure, where the automatic checks do not repeat a notification for the same failure. With the interval and check-on-open off, Hoserva contacts the catalog host only on that manual check. An unchanged catalog answers `304` and downloads nothing.
- **Audit log** of configuration changes and destructive actions, with actor and timestamp.
- **Local logins can read shared array data.** Share files are created `0664` under `2775` directories (Q26), so any login on the host can read them. The logins on the host are the admin's own — an SMB-only account is locked and has `nologin` — so this is accepted rather than tightened (Q92); what a local login must never do is make the root daemon write, remove, read or list through a path it controls.
- **Build inputs are trusted.** The release build job installs packages from the distribution mirrors and resolves Go and npm dependencies, and the signing job signs what that job uploaded. The signed checksums prove an artefact is what the build job built, not that the inputs it built from were clean, so a compromised mirror package or dependency that runs during the build is not stopped by the key separation (the signing key and the catalog key are never in the build job's reach). This is accepted: the build uses the distribution's and the language ecosystems' published packages rather than rebuilding them.
- **The guard judges a diff, not the sync's own scan.** The threshold guard evaluates a fresh diff immediately before every sync, and `snapraid sync` then makes its own scan, so a change made to the array in the interval between the two — an encryption event that starts then — is synced without the guard having judged it. The interval is one diff's run. This is accepted: closing it would mean Hoserva scanning the array itself, where D1 has it drive `snapraid`; every other path to parity stays behind the guard.
- **An appdata archive without a tag is authenticated only by being the age-encrypted file.** Archives written before they carried a MAC (doc 10 §2) are accepted from a destination that encrypts (a remote, or a local one with `encrypt` on) as the `.age` file, on the ground that only the box could have encrypted to its recipient. The public recipient is not secret, though: it is stored in the clear in `state.db`, and so it is inside an unencrypted config archive. Someone who can read one of those and can write an encrypting destination can therefore place an archive of their own that is accepted as a legacy archive. This is accepted rather than closed, because closing it would make every legacy archive on an encrypting destination unrestorable from the UI, and the damage is bounded: an admin still has to choose to restore the archive, a restore still replaces only the restored container's own directories inside the appdata location, and a setuid bit on an entry owned by uid 0, or a setgid bit on one owned by gid 0 or by a root-equivalent group (`hoserva`, `sudo`, `disk`, `docker`, `kmem`, `shadow` or `libvirt`, resolved at restore time), is never restored. Every archive Hoserva writes now carries the tag, which does not rely on the recipient at all.

### Threat model

Doc 15 is the threat model: the attackers and what each is trusted with, the entry points and the code that owns them, the numbered security invariants, the severity rubric and how a finding's severity decides where it is reported. The accepted residuals above are listed there as well and stay accepted. A finding rated Critical or High is reported privately, through a security advisory, and a lower one as a public issue (Q91); `SECURITY.md` tells outside reporters how.
