# Hoserva — Backup Strategy

## The scope question

*Is everything except the internal SQLite DB the user's problem, to be solved with third-party tools of their choice?*

**No — but the line is not where it first appears.** The right split is by **who is uniquely positioned to back it up correctly**, not by what is convenient.

| Data | Owner | Reason |
|---|---|---|
| **Hoserva config** (SQLite, generated configs, templates) | **Hoserva** | Only Hoserva knows its own schema and what a consistent snapshot looks like |
| **Container appdata** (on cache, outside parity) | **Hoserva** | Requires stopping containers in the right order; Hoserva is the only thing that knows which containers exist and which are running |
| **VM vdisks and domain definitions** (Phase 3.5, doc 14) | **Hoserva**, off by default | Only Hoserva knows which VMs exist, whether they're running, and that a vdisk must not be copied while its QEMU process holds it open — but a full vdisk copy is large enough that opting in should be a deliberate choice, not a silent default |
| **Bulk user data** (media, documents, the pool itself) | **The user** | Terabytes, wildly varying requirements, mature tools already exist |
| **Off-site replication** | **The user**, with Hoserva making it easy | rclone, restic, Borg, Duplicati all do this better than a NAS UI would |

The reasoning: **back up what only you can back up correctly, and get out of the way for everything else.**

A user can point restic at `/mnt/user/documents` without Hoserva's help. A user cannot easily produce a consistent appdata backup without knowing which of their 23 containers hold a SQLite database that must not be copied while running — and that is exactly the knowledge Hoserva has.

Building a general-purpose backup product inside a NAS is also the road to becoming a worse Duplicati. The three shipped backup jobs below are narrow, well-defined, and each exists because leaving it out creates a specific, known data-loss scenario.

## 1. Config backup

### What it contains

```
hoserva-config-<id>-2026-09-14T03-00-00.tar.zst
├── manifest.json            version, timestamp, host, checksums
├── state.db                 SQLite, consistent snapshot via VACUUM INTO
├── secrets.age              secret columns and stack .env files, under the backup passphrase (Q28, Q80)
├── identity.age             the onboarding recipient's own private identity, under the backup passphrase (Q80)
├── generated/               whatever else is in /etc/hoserva besides *.custom.conf and dot-files (see below)
├── stacks/                  every docker-compose.yml (their .env files are in secrets.age)
├── templates/               installed app templates
├── custom/                  user-owned config (smb.custom.conf etc.)
├── host/                    only in a bare-metal restore's pre-import archive: the host files it replaced
└── snapraid-content/        SnapRAID content files (optional, large)
```

For a destination that encrypts (below), what actually leaves the box is two files, not one:
`hoserva-config-<id>-2026-09-14T03-00-00.tar.zst.age` — the tree above, age-encrypted whole to the
onboarding recipient's public key — and a small sidecar,
`hoserva-config-<id>-2026-09-14T03-00-00.tar.zst.age.identity.age`, carrying the same private identity
as `identity.age` above, age-scrypt-encrypted under the backup passphrase on its own. They are
two files because age's own format refuses to combine a scrypt recipient with any other
recipient in one encrypted file — a restore recovers the identity from the sidecar with the
passphrase, then uses it to open the main archive; the box itself can also open the main archive
directly with its own copy of the identity, without the sidecar or the passphrase at all.

Not included: `metrics.db` and job logs (Q74) — history, not configuration.

**What `generated/` holds, and where the generated files are not.** `generated/` and `custom/` are both filled from one directory, the config root `/etc/hoserva`: `custom/` with its `*.custom.conf` files, `generated/` with every other file in it except dot-files. `config.Generator` writes into that directory only the user-owned `smb.custom.conf` (an include for `smb.conf`, which goes to `custom/`), so a file it generated is never in `generated/`. Each of the others is written at its host path under `/etc` and is in neither directory: `snapraid.conf` (`/etc/snapraid.conf`), the disk, pool and storage-target mount units (`/etc/systemd/system/`), `smb.conf` (`/etc/samba/smb.conf`), the NFS `exports` (`/etc/exports`), the NUT files (`/etc/nut/`). The archive does not carry them, because the database is their source and a restore regenerates them (D4; *What an in-place restore restores*). The only copies of `smb.conf` and `exports` an archive holds are in the `host/` of a bare-metal restore's pre-import archive, and those are the new host's own files, not the exporting system's.

### Consistency

**Never copy a live SQLite file.** Use `VACUUM INTO '<path>'` (or the backup API) to produce a consistent snapshot without stopping the daemon. A `cp` of a WAL-mode database mid-write yields a file that restores as corrupt, and does so intermittently, which is the worst kind of bug.

**Secrets** (SMTP passwords, notification tokens, API keys, Let's Encrypt keys) are handled in two layers (Q28), because the daemon must use them unattended — a 03:00 disk-failure alert cannot wait for someone to type a passphrase:

- **At runtime**, secret columns are encrypted with a machine key in `/etc/hoserva/secret.key` (root, `0600`, generated at install). This protects against the database file leaking — in a diagnostics bundle or a copied backup.
- **In backups**, the secrets section is re-encrypted under a **backup passphrase** the user sets during onboarding (doc 03 §1). The machine key itself is never included. `secrets.age` carries the sealed database columns for ACME, UPS, backup-destination and **notification-channel** credentials (one entry per channel that has one: the SMTP password, Gotify or ntfy token, Discord webhook URL or webhook auth header), plus the stacks' `.env` files. TOTP secrets are deliberately not carried; they are cleared and re-enrolled after a restore onto another installation. A backup restored without the passphrase restores everything except secrets, and says so clearly.
- **Off-box, the whole archive is encrypted** with age before it leaves the box (Q80). An onboarding age recipient (X25519) is generated exactly once, at first start; the box keeps only its public half in the clear, and the matching private identity is kept at rest only wrapped under the machine key — never in the clear — so the daemon can use it unattended, the same reasoning as the machine key itself. Every destination other than a local path always encrypts; a local path may opt in.

  Encrypting to the recipient alone would strand every off-box archive the moment the box holding the private identity is lost, so the private identity also travels with every encrypted archive, itself wrapped under the backup passphrase (age's scrypt mode, `identity.age` above): a restore recovers it with only the passphrase, then uses it to open the archive, and can go on protecting future archives with the same recipient rather than starting a fresh one. **A restore of an *encrypted* archive needs the passphrase — there is no path around it, because the passphrase is what unlocks the identity that unlocks the archive.** This is stricter than the secrets-only case above: losing the passphrase for an off-box archive, with the box itself gone too, loses the whole archive, not only its secrets section. A *local, unencrypted* archive is unaffected — state.db and every plain file restore exactly as they do today, and only its embedded secrets.age is passphrase-gated. A remote destination can't be added until a backup passphrase is set.

### Schedule and retention

- Default: nightly, as the last step of the maintenance chain (Q30), plus automatically before every self-update and every array-topology change actually starts, including one that waited behind another topology job in the queue first
- Retention: keep 7 daily, 4 weekly, 6 monthly, pruned per destination
- Each backup is small (single-digit MB without content files), so retention is generous by default
- **Pre-change exemption (#401):** the pre-import safety backup (`POST /config/import`), the pre-update backup (the self-update path) and the pre-topology backup (below) mark their archive with that reason in its filename (`hoserva-config-<id>-<timestamp>.pre-import.tar.zst`, `.pre-update.`, `.pre-topology.`). Retention keeps the **5 most recent pre-change archives per destination** in addition to the daily/weekly/monthly tiers above, so a second same-day change never prunes the one copy of the state from before the first. A pre-change archive beyond that bound falls back to the ordinary tiers like any other archive. Archive filenames carry second resolution, with a numeric suffix on collision, so two backups in the same minute — or the same second — never overwrite each other; an archive written before this fix, with the original minute-only name and no reason marker, still parses as an archive (and is pruned only where retention below claims legacy archives).
- **Pre-topology backup (#406, #408):** every job in doc 01 §4's Topology class — disk format, disk add, disk remove, disk replace, data or parity disk upgrade, and pool remount — runs this backup at the moment it actually starts, not at the moment it is submitted: the two are the same instant for a job that starts immediately, but not for one that has to wait behind another Topology, Parity or Array-write job first (doc 01 §4's own mutual exclusion), since a snapshot taken at submit time would describe the configuration from before whatever is currently running finishes, not from just before this job's own change. `job.Scheduler.Submit` runs it itself for a job starting immediately, once the job's admission checks pass and before the job row is created — a submission admission refuses (maintenance mode, a database restore, an array not stopped for a data-disk upgrade, an on-battery hold) writes no archive, so refused retries never take the pre-change retention slots a real pre-import or pre-update archive relies on, and the admission checks run once more after the backup, in the same step that creates the job; `dispatch()` runs it for a queued job at the moment its turn comes, once whatever it was waiting behind has finished, and before its own run function is ever called — so a future Topology job type is covered by construction rather than needing its own call site either way. The behaviour matches the pre-update backup: an unconfigured backup (no `job.Scheduler.SetTopologyBackup` wired at all) skips it rather than failing. A backup that fails once wired refuses the change outright: for a job starting immediately, no job row is created at all and the caller sees why; for a queued job whose type has no cleanup to run (`job.AbortFunc`, doc 02 §4), it ends failed with the backup's error recorded, its run function is never called, and the rest of the queue keeps moving. A queued job cancelled while this backup is dispatching, or whose type does have one — a data-disk upgrade's Unwind, doc 02 §4 E3 — runs that cleanup first, before either outcome is recorded (doc 02 §4 invariant 3: `cancelled` and `failed` both mean the type's own cleanup already succeeded): it ends cancelled, or failed with the backup's error, only once the cleanup succeeds, and interrupted with the cleanup's own error instead if it does not, leaving the job resumable exactly as a plainly queued or interrupted job's own failed Cancel already does. A data-disk upgrade resumed at its releasing checkpoint is the one exception: past that release decision it is no longer cancellable and doc 02 §4 invariant 4 makes `succeeded` the only outcome left, so there is nothing for Unwind to undo — Cancel already refuses it outright, and a failed start-time backup for it skips Unwind entirely and leaves the job interrupted at its unchanged checkpoint with the backup's own error, resumable once the backup destination is fixed, never `failed`. This is orchestrated the same way as the pre-import and pre-update paths: `internal/backup` implements the archive itself, `internal/job` only calls it through the small `Run(ctx) error` interface it already used for the nightly chain's own last step.
- **The pool destination while the array is stopped (#409):** a destination path under the pool's own catch-all mount root (doc 02 §1, Q12) is never written to unless that mount root is confirmed mounted first, using the same stat-based check the pool's own mount lifecycle already relies on. With the array stopped — every data-disk upgrade's own pre-topology backup runs in exactly this state (doc 02 §4 E8, UR3) — the catch-all path is a bare, empty directory on the boot device's own root filesystem; without this check a backup would create the destination there and write into it, reporting success, and that archive would be silently hidden the moment the pool mounted back over it. A `backup.PoolWriteGate` closes that check's own remaining race: `job.ArraySequence.Stop` closes it, refusing every new pool-destination write and waiting for any already admitted to finish, **before** it unmounts anything — every stop path that unmounts, including the rollback of a failed `array start`, shares this one call — and `Start` re-opens it only once the pool is actually mounted again. A write refused this way is **skipped and recorded as such**, exactly like an unmounted pool, never an error on its own: the boot destination (a separate failure domain, unaffected by the array's own mount state) still captures the change. A run left with nothing actually written anywhere — every enabled destination skipped or itself failing — is a failed run: a pre-change backup (pre-import, pre-update, pre-topology) still fails closed and refuses the change it guards rather than reporting a snapshot that was never taken. This gate is not specific to the pre-topology backup: every `backup.Service.RunReason` caller — the pre-import safety backup, the pre-update backup, the nightly chain, and every pre-topology backup alike — shares the one instance `cmd/hoservad` wires into both `backup.Service` and `job.ArraySequence`, so none of them can race the unmount of a stop in progress within this daemon's lifetime: the gate refuses a pool write from the point `Stop` reaches its unmount steps — after running jobs and share mutations have drained, services have stopped and the storage-target gate has closed, immediately before the first unmount — until `array start` has mounted the pool again, and `Close` waits for any pool write admitted before that point. It does not survive a restart — `poolWriteGate := &backup.PoolWriteGate{}` starts open, and `RestorePersistedMaintenance` restores only the persisted array-stopped state, not the gate — so after a reboot with a persisted `array stop` (the usual stop → power off → swap disk → boot → upgrade sequence), the gate is open and the mount check above is the only thing keeping a write off the still-unmounted pool; the mount check is required for this case, not redundant with the gate. A data-disk upgrade's own pre-topology backup runs at `Submit` only once the job's UR3 admission (doc 02 §4) has passed — the stop sequence has completed and the pool is unmounted, so its pool destination is skipped (by the closed gate, or after a reboot by the mount check above); `ArraySequence.Stop`'s own `Close` call still waits for any pool write admitted before that point to finish before its unmount runs.

### Multi-destination — yes, from v1

This is the right call. A config backup stored only on the array it describes is not a backup, and a user whose boot device and array both fail is exactly who needs it most.

Destination types:

| Type | Notes |
|---|---|
| **Local path** | Anywhere on the pool or an external disk (Q72). Always available. |
| **SMB share** | Another NAS, a router USB disk. rclone has no NFS client, so an NFS share is a **local path** at wherever the host has mounted it. |
| **S3-compatible** | Backblaze B2, Wasabi, MinIO, Hetzner Storage Box |
| **SFTP / SSH** | A VPS, another homelab box |
| **WebDAV** | Nextcloud, pCloud, Koofr |
| **rclone remote** | If rclone is present, any of its 70+ backends via an existing remote name |

Implementation: **rclone as an optional dependency (`Recommends:`, Q41) covers everything except local paths.** Rather than writing six protocol clients, Hoserva writes the archive locally and shells out to `rclone copy` for remote destinations. This is the same "orchestrate, don't reinvent" principle as D1, and it means every backend rclone gains, Hoserva gains.

Per-destination configuration: enabled, schedule, retention, encryption (always on for remote destinations, optional for local paths — Q80), and a **Test connection** button that actually writes and reads back a file. An untested backup destination is decoration.

**How destinations work (#60).** Destinations are rows in SQLite (`backup_destinations`, D4) and are read on every backup run, so one added through `POST /backup/destinations` receives the next backup without a restart. A fresh install (or one upgraded from before destinations were stored) is seeded with Q40's two local destinations, boot and pool, only while no destination exists at all, both in one transaction so an interrupted start leaves none and the next start seeds both. `GET /backup/destinations`, `POST /backup/destinations`, `DELETE /backup/destinations/{id}` and `POST /backup/destinations/{id}/test` are the whole surface; `backup.PrepareDestination` is the admission check the daemon and `cmd/mockapi` both run for a destination added through the API, and `backup.PrepareExternalDestination` the one they both run for an external disk's destination.

- **Types and options.** `local`, `smb`, `s3`, `sftp`, `webdav` and `rclone`. A remote type takes only rclone's own option names from a fixed list per type (for example `s3`: `access_key_id`, `provider`, `endpoint`, `region`, plus the `secret_access_key` credential; `sftp` verifies the host key only when `known_hosts_file` is given); anything else is refused, so a request cannot inject an arbitrary rclone option. `rclone` names a remote already configured in rclone's own config.
- **How rclone is invoked.** `rclone copy --immutable <local file> <remote>:<path>` with an argv — never `sh -c`. The remote is configured through `RCLONE_CONFIG_HOSERVADEST_*` environment variables, not argv, so a credential is not visible in the process list; a password is passed in rclone's obscured form (`rclone obscure -`, from stdin). After each upload a listing confirms the file is there at its written size. Every rclone call has its own deadline. Credentials are sealed under the machine key (Q28), never returned by the API (`hasSecrets` only) and included in `secrets.age` like the other database secrets.
- **rclone missing.** Adding a remote destination without rclone installed fails with `424 rclone_missing`, whose message carries the install command (`sudo apt install rclone`, Q41) — nothing is stored. Local destinations never need rclone.
- **Encryption.** A remote destination is always encrypted (Q80): `POST /backup/destinations` refuses one with `400 backup_passphrase_required` while no backup passphrase is set (`backup.ValidateRemoteDestination`), an explicit `encrypt: false` is refused, and `Service.Run` never writes an unencrypted archive to a remote even if a stored row says otherwise. The archive and its identity sidecar are what `rclone copy` uploads. The connection test's file is random bytes with no archive content, so it is not encrypted.
- **Test connection** writes a small file through the same write path a backup uses, reads it back, compares it and deletes it. A destination that cannot be reached is a `200` with `success: false` and the reason; a pool destination is not written to while the pool is unmounted (#409), nor an external-disk destination while its disk is ejected, so its test reports that instead of creating the directory on the boot device.
- **Retention** is applied per destination after each write — on a remote by listing it with `rclone lsjson` and removing with `rclone deletefile` (an archive's identity sidecar goes with it). It only ever removes archives this installation wrote. Every archive name carries a 12-hex installation id (`hoserva-config-<id>-<timestamp>…`), a hash of the onboarding recipient's public key, which is generated once per installation and never rotated (Q80); a destination shared with another installation (one storage box, one bucket prefix, one NFS mount) therefore keeps each installation's archives under that installation's own retention, and neither counts the other's towards its tiers. An archive without an id was written by an earlier release; it is only claimed on the boot and pool default destinations, local directories on this installation's own boot device and pool that earlier releases wrote to and nothing else does, and there it ages out under the ordinary tiers — on any other destination it is left alone, since it cannot be shown to be this installation's. Anything else in the directory is left alone as well.
- **Local directories.** A destination directory that does not exist is created private (`0700`); one that already exists keeps its mode and owner, since it may be a share other users rely on. Archives themselves are `0600`. `POST /backup/destinations` refuses a local path in a system location (`/etc`, `/usr`, `/boot`, `/proc`, `/sys`, `/dev`, `/run`, `/tmp` and `/var` themselves, and anything under the first seven), a symlink into one, and the daemon's own state and configuration directories (except the state directory's `backups` subdirectory, the boot default).
- **External-disk destinations (Q72).** Marking an external disk as a backup destination (`backupDestination: true` on `PATCH /disks/external/{label}`, or on registering it) creates the destination `external:<label>` — a local destination at `/mnt/disks/<label>` with the default retention — in the same SQLite transaction that sets the disk's flag; clearing the flag deletes that destination in the same transaction, and archives already written to the disk stay where they are. `DELETE /backup/destinations/external:<label>` clears the disk's flag in the same transaction too, so the flag and the destination never disagree (a flag found set without its destination, as one set before the flag created it leaves it, is given its destination when the daemon starts). The flag is refused with `409 backup_destination_exists` while another destination already has the disk's name or path. A local destination under `/mnt/disks/<label>` — this one, or a path added by hand — is admitted for a write only after `/mnt/disks/<label>` is confirmed to be a mount point in the kernel's mount table (`/proc/self/mountinfo`, read without listing or reading the disk — Q13): an ejected disk is skipped with a logged reason instead of having its directory created on the boot device. The same refusal applies to its connection test, and a mount table that cannot be read counts as not mounted. The mount is confirmed once, when the destination is admitted, so the check alone cannot stop an eject that lands between it and the write. Every write to (or read from) a destination on the disk therefore holds a per-disk slot, taken before the mount check and released after the write and prune. `POST /disks/external/{label}/eject` closes that disk's gate first: it refuses new writes, **waits for a backup write in flight to that disk to finish** (up to two minutes), and only then unmounts. If the wait runs out the eject fails with `409 external_disk_busy` and the disk stays mounted and open to backups; an unmount that fails reopens the gate too. A write attempted after a completed eject is skipped with a logged reason, like an unmounted disk, and the gate stays closed until `POST /disks/external/{label}/mount` succeeds. The one gate instance is built in `cmd/hoservad` and shared by `backup.Service` and the external-disk handler; other disks and the pool destination's own gate are unaffected. A skipped external destination gets no success recorded, so it raises `backup_destination_stale` like any other destination that stops being reached; nothing mounts the disk for a backup (Q72).
- **Partial failure.** Every enabled destination is attempted in turn. If at least one archive was written, a destination that failed is logged and the run succeeds; it shows up through its own last-successful-backup time. A run that wrote nowhere fails, as it always has.
- **Stale destinations.** Each destination stores `lastSuccessfulBackupAt`. An enabled destination that has gone 48 hours without a success — counted from its creation until its first — is stale, and the schedule tick that already runs every minute publishes `backup_destination_stale` once for it, again only after a success has ended the staleness and a later one begins. The check reads stored timestamps only; it never lists or reads a destination, so nothing on a timer walks a disk (Q13).

### Verification

A backup that has never been restored is a hypothesis. Hoserva therefore:

- Verifies the archive after every write (checksum, and confirm the SQLite snapshot opens and passes `PRAGMA integrity_check`)
- Runs a **monthly automated restore drill**: extract the newest backup into a temp directory, validate schema and checksums, discard. Failure raises a high-priority alert. (Below.)
- Shows **last successful backup per destination** on the dashboard's attention row when any destination is stale

#### The restore drill (#63)

`backup.Service.RunDrill` is the whole drill, and the `restore_drill` job (service class, not resumable) is a thin runner of it. It tests what a restore would be given, not what the box wrote a moment ago, so it never uses a local copy of an archive:

- **Which archive.** For **each enabled destination in turn**, the newest archive this installation wrote to it, listed the way retention lists it (an archive of another installation sharing the directory, or a legacy one on a destination that does not claim them, is not this installation's and is not tested). Every destination is tested because a rotten archive on the off-box destination is exactly what a drill exists to find, and it would never be picked if only the single newest archive across all of them were. A pre-import, pre-update or pre-topology archive counts as the newest like any other.
- **How.** The archive is fetched from the destination into a temporary directory the drill creates and removes (through `rclone copyto` for a remote, so a remote drill downloads and never writes). An age-encrypted archive is opened the way it is opened once this box is gone: its identity sidecar is decrypted with the backup passphrase, and the recovered identity opens the archive, not the box's own copy of the identity. Then `VerifyArchive` runs on the plaintext archive: it unpacks it into a second temporary directory, checks every manifest checksum, opens `state.db` and runs `PRAGMA integrity_check`, and, when the archive has a `secrets.age`, decrypts it with the passphrase. Everything fetched or extracted is removed on every path. The live `state.db` is never opened and nothing is written to a destination.
- **Against a backup running at the same time.** Config backups are not scheduler jobs (the nightly chain, an import and a topology job each take one), so nothing in the job system keeps them apart from the drill. Inside the daemon they exclude each other on the destination: a backup's write and prune of a destination wait for a drill's listing and fetch of it (a lock in `backup.Service`, not a job scope), and the other way round. The archive a drill picked therefore cannot be pruned before it is fetched, and a drill never reports as failed an archive that was only pruned. An archive that is missing despite this (removed from the destination by something other than a Hoserva backup) is not retried against another one: it fails the drill.
- **What fails it.** Anything that stops the check from concluding the archive restores: a destination that cannot be listed or read (including a pool destination while the pool is not mounted), one holding no archive of this installation, an archive that does not fetch, decrypt or verify, an encrypted archive with no backup passphrase set, a sidecar the passphrase does not open. The drill passes only if every enabled destination passed; with no enabled destination it fails, since there is nothing to restore from. A drill cancelled by the operator concludes nothing: it records no result and alerts on nothing.
- **Result and alert.** The result replaces the single row in `restore_drill_result` (time, pass or fail, and per destination the archive tested and the reason it failed) and, on failure, publishes `restore_drill_failed` (error severity). Both are attempted whichever the other does, and the job fails with every part that failed, so a result that could not be stored or an alert that could not be sent is in the job history and not swallowed. A scheduled drill that could not even be queued (maintenance mode, say) is recorded and alerted the same way, and is not retried before the next window. A drill the daemon's restart interrupts is not resumed and records nothing, so `ranAt` of the last result going stale is how that shows.
- **Running it.** `GET /backup/drill` returns the last result (`lastRun` is absent until the first drill) and `POST /backup/drill` queues a drill now, behind another drill if one is running. The schedule's `restore_drill` entry runs the same job monthly through the generic other-jobs tick (the window is claimed before the job starts, as for the appdata backup); its default is **on**, monthly at 05:00, per §4. A schedule row stored before the default changed keeps the settings it has — rewriting a stored row would be a data transform — so an installation that already has the disabled row turns the drill on in the schedule settings. The drill reads a destination's archive listing and one archive; it never walks a data disk (Q13).

### Restore

Two paths:

**In-place restore** — from the UI, for rolling back a bad config change. Preview what will change, then apply.

`POST /config/import` refuses, before anything is written (no pre-import backup, so a refused retry takes no pre-change retention slot, no restore hold, no change to the database), an archive it cannot safely restore in place:

- **Not a sound archive** (400 `invalid_archive`): verification covers the whole archive, not only what the manifest lists. The manifest must list exactly the regular files the archive holds (a file it does not list, or a listed file that is missing, is refused), and the archive may hold only regular files and directories, each name once (a symlink, hardlink, device, FIFO or repeated name is refused). This is the same check the nightly chain and the restore drill run.
- **Another installation's archive** (409 `archive_other_installation`): its `state.db` has no `machine_key_check` row or a different `check_value` from the live one. Restoring it would replace `machine_key_check` and `backup_recipient`, and the next start would fail the machine key check (Q28). Another installation's archive is restored only onto a fresh install (bare-metal flow, #276).
- **A file it would restore lands somewhere it must not** (409 `restore_path_unsafe`): a `*.custom.conf` in the config root, a stack file, or a directory on the way to one, that is a symbolic link or not a regular file/directory, a category directory (config root, templates, stacks) that is a symbolic link, or an archive path that is not one of the files its category holds (`custom/` holds only `*.custom.conf`, `stacks/<name>/` only a compose file or `meta.json`). Nothing is followed and nothing is written outside the three directories. Checked by `backup.PlanFiles`, before the pre-import backup.
- **A passphrase that does not open the secrets** (400 `backup_passphrase_incorrect`): the request gave a `passphrase` (the CLI's `--passphrase-file`) and it does not open the archive's `secrets.age`. It is the only passphrase tried then, so a wrong one is never quietly replaced by the configured one. An archive with no `secrets.age` has nothing to check it against, and is not refused for it. A `secrets.age` that cannot be read at all is refused as `invalid_archive`.
- **A different array** (409 `archive_array_mismatch`): the archive's `array_disks` (role, role index, filesystem UUID, WWN, serial and `removal_state`, not the device name), `relocation_manifest` or `relocation_removing_disks` differ from the live ones; the message names each difference. The disk lifecycle jobs (doc 02 §4, doc 09 §4) are the only path that changes the array, so an in-place restore that would change it, or undo a relocation, is refused instead of half applied, and the pre-topology archive of a job that has since finished is refused the same way. Shares, users, groups, schedules and notification and backup settings, which is what an in-place restore rolls back, are never refused.

The schema-version match (400 `incompatible_archive`) and both comparisons above are `backup.CheckImport`, run before the pre-import backup and again once the scheduler's restore hold is taken, so a topology job that finishes in between cannot be restored over. Any failure to read either database also refuses.

**Preview.** `POST /config/import/preview` (`previewConfigImport`, admin) takes the same multipart `archive` as `importConfig`, no `confirm`, and answers synchronously, since it reads one upload and one SQLite file: it is not a job, and it never walks a data disk (Q13). `hoserva config import --preview <archive>` calls it (`--json` prints the response) and refuses to be combined with `--confirm`. It reports:

- **The archive**: the manifest's timestamp, host and Hoserva version, the archive's database schema version, and the running database's.
- **`blockers`**: the refusals `importConfig` would return for this archive, with the same code and message, from the same `backup.CheckImport` call (`incompatible_archive`, `archive_other_installation`, `archive_array_mismatch`, `restore_path_unsafe`). A running job, which is not a property of the archive, is not among them; `importConfig` still refuses on it. An archive that cannot be read is refused outright, as `importConfig` refuses it (400 `invalid_archive`, 413 `archive_too_large`, and 501 `not_configured` when the daemon has no config backup wired), before any comparison.
- **`groups`**: one entry per category, always in this order, each with the items an in-place import would `added` (in the archive, not live), `changed` (in both, with different content) and `removed` (live, not in the archive). Rows are matched by primary key between the staged `state.db`, opened read-only, and the live database, and each item is named as a user knows it (a share name, a username, a schedule job, a destination name; `share / user` for a permission, `event / channel` for a route). The categories are shares and share permissions; users, groups, group memberships and API tokens; schedules; notification channels, routes, severities and quiet hours; backup destinations, appdata backup settings and the backup recipient; and system settings: ACME, UPS, array settings, the host configuration decisions (by kind), registered external disks (by label), and the settings kept on the installation row: hostname, timezone, backup passphrase, update channel and update check. A secret or the backup passphrase is compared, so a change to it is listed by its kind, and its value is never returned. Columns that record what the system did rather than what was configured (`updated_at`, the last-run and last-login timestamps, a destination's last-success and stale-alert times, ACME's last error, when a host decision was applied) do not make a row changed. The list is empty when the schema versions differ, since the databases cannot be compared row by row. After those come the files an import restores besides the database (`backup.PlanFiles`, reading only the config root, the templates and stacks directories and the extracted archive): `custom_config` (custom config files), `templates` (app templates) and `stacks` (app stacks), each item a file named by its path relative to its directory (`stack/file` for a stack), `added` when only the archive has it, `changed` when both do with different content, `removed` when only the disk has it. A new category is another entry of the same list.

  Every table an import replaces is compared or classified, and a test lists the schema's tables and fails on one that is neither, so a new table cannot slip past the preview. The tables not listed are of five kinds: history and runtime state (jobs, audit log, spin events, notification deliveries and alerts, share usage, mover and cache results, the last restore drill), which is not configuration; sessions, which `notes` covers; the array tables (`array_disks` and the relocation tables), the installation's machine key check and the schema version, which `blockers` covers because an archive that differs in them is refused; `array_maintenance`, which the import keeps (below) and `notes` reports; and the installation row's installation id, creation time and previous version, of which the first cannot differ in an archive `blockers` lets through and the others record what the system did.
- **`secrets`**: whether the archive's stack `.env` files would be restored. `status` is `none` (the archive has no `secrets.age`), `opened` (the passphrase given, or else the configured one, opens it), `no_passphrase` or `passphrase_incorrect` (the configured one does not; an explicit one that does not is refused as in the import, 400 `backup_passphrase_incorrect`). `stacks` lists, unless it is `opened`, the archive's stacks whose `.env` files would not be restored. `previewConfigImport` takes the same optional `passphrase`, and the CLI the same `--passphrase-file`.
- **`bareMetal`**, on a fresh install only (no array configured): whether the archive's database would be upgraded, each array disk the archive records with the attached disk it matched and its state, and the mapping to confirm, as *Bare-metal restore* below describes. On a fresh install the blockers are `archive_newer_version` (no `bareMetal`), `incompatible_archive` for an archive that cannot be upgraded, and `restore_path_unsafe`, and `groups` compares the archive's database as the restore would leave it (upgraded, with this installation's key rows kept and the sealed secrets cleared) with the live one.
- **`notes`**, always `sessions_replaced` (the archive's sessions replace the live ones, which signs the current user out) and `array_state_kept` (the running array's state stays as it is; see below), and on a fresh install `host_files_replaced` when the restore will write over a Samba or NFS file already on this host (see *What the restore does* below). That note is one entry that names every such file at its path on this server, so the Restore section shows it with the others.

**What an in-place restore keeps.** The array's maintenance and stopped state (the `array_maintenance` row, doc 02 §4) is not restored from the archive. It records the machine's physical state, such as an `array stop` for a disk swap, not configuration to roll back: restoring an archive taken in normal operation, or one with no such row, would return a stopped array to normal operation, and the scheduler would admit every job type and the storage-target gate could remount the pool over a disk the user believed was still out. `importConfig` therefore reads the live row, or its absence, under the scheduler's array-state lock and writes it into the staged copy of the archive's `state.db`, so the restore, one write transaction, leaves the row exactly as it was and no job is ever admitted under the archive's state; the running scheduler's own in-memory state is untouched, so it and the database keep agreeing, and after a restart the persisted row restores the same state. If the live row cannot be read, or the staged copy cannot be written, the import fails before the live database is written. The alternative, refusing an import while the array is stopped, would block the restore a user most likely needs mid-recovery, so the state is kept instead.

**What an in-place restore restores.** The database, then three categories of files, then every managed config file regenerated from the restored database (D4):

- **Custom config** — the archive's `custom/` (`*.custom.conf`) into the config root, **templates** — the archive's `templates/` into the templates directory, **stacks** — each `stacks/<name>/` compose file and `meta.json` into the stacks directory. Each category matches the archive afterwards: a file the archive lacks is removed. A restore touches a stack's `.env` only through the secrets described below, and never any other file in the stacks directory or the config root, or appdata. A file whose content already matches is left alone. `backup.RestoreFiles` is the one function that does this, from an archive tree already extracted and verified and the `Paths`, returning what it replaced, added and removed per category, a stack's `.env` not among them; the bare-metal flow (#276) calls it unchanged, with `backup.WithStackEnvs` for the `.env` files.
- **Secrets.** The one part of the archive an in-place restore needs a passphrase for is the stacks' `.env` files, which live only in `secrets.age` (Q80). The database's own secret columns (ACME, UPS, backup-destination and notification credentials) are in the restored `state.db` sealed under this installation's own machine key, which an archive of this installation is restored under (another installation's is refused above), so they come back with the database and need no passphrase (Q28). `backup.ResolveSecrets` decides what can be opened: the `passphrase` the request gave if there is one, and otherwise the configured backup passphrase. `backup.ReadSecrets(tree, passphrase)` is the reader, which #276 reuses to re-seal the database secrets under another installation's machine key. When `secrets.age` opens, each of its `.env` files for a stack the archive holds files of is written to `<stacks>/<stack>/.env` with mode `0600`; an entry for any other stack is ignored and reported. The files are staged with the stacks category's and swapped in with it (`backup.WithStackEnvs`), so a failure leaves every stack's files, `.env` included, wholly as they were or wholly as in the archive. A stack directory the archive lacks keeps its `.env`, as does one whose `.env` the archive has none of, and the report says so. An `.env` that is a symbolic link, or a stack directory that is, is refused as any other file is (409 `restore_path_unsafe`), before anything is written.
- **The pre-import archive's secrets.** The import deletes each live `.env` it replaces once it has finished, so the pre-import safety archive has to hold them. When the import restores `.env` files, that archive's own `secrets.age` is sealed with the passphrase that opened the imported archive's (`backup.SealSecretsWith`): the `passphrase` the request gave, or the configured one when that is what opened it. With no backup passphrase configured this is what gives the pre-import archive a `secrets.age` at all; a configured passphrase that differs from the request's does not seal it. The archive is verified against that passphrase like any other. If the pre-import archive cannot be built, its `secrets.age` included, the import is refused before anything is written, as any failed pre-import backup is. An import that restores no `.env` (no passphrase opens `secrets.age`) takes the pre-import archive as before: sealed with the configured passphrase, and with no `secrets.age` when none is configured. The identity sidecar and an encrypting destination's artifacts always use the configured passphrase, which an encrypting destination requires.
- **Without a passphrase that opens it**, no `.env` is restored and everything else is: the archive has no `secrets.age` (`none`), no passphrase is configured or given (`no_passphrase`), or the configured one does not open it (`passphrase_incorrect`). The import still succeeds, and the report says which.
- **The restore report.** `importConfig` answers `200` with the report, where it used to answer `204`: `restored`, one entry per category in the preview's order and then `stack_env`, each with the number of items `added`, `changed` and `removed` (what was identical is not counted; an `.env` is counted by stack); `notRestored`, each item with a kind (`stack_env`), the stack, a reason and a message; `secrets`, the same status the preview gives; `preImportArchive`, the name of the pre-import safety archive, empty when no destination was written to; and `preImportSecrets`, which passphrase seals that archive's `secrets.age`: `request` (the one given with the import), `configured` (the configured backup passphrase) or `none` (it has no `secrets.age`), never the passphrase itself, so the user knows what to use to go back. The reasons are `no_secrets`, `no_passphrase` and `passphrase_incorrect` (for each stack of the archive, since its `.env` is not restored), `stack_not_in_archive` (the secrets hold an `.env` for a stack the archive has no files of) and `left_in_place` (a stack on this machine has an `.env` that nothing replaced). The database's counts are the same comparison the preview makes, taken before the restore. `hoserva config import --confirm` prints the report, or the JSON with `--json`, and `--passphrase-file <file>` reads the passphrase from a file (one trailing newline removed; an empty file is refused). The CLI's report also says which passphrase seals the pre-import archive's secrets.
- **The archive's `generated/` is not copied back.** The database is the source of every managed file, so restoring `generated/` could only let a stale file win; the directory stays in the archive as verified content.
- **One tree.** `importConfig` extracts and verifies the archive once (`backup.ExtractVerifiedArchive`), and everything is restored from that tree. Only files the manifest lists are restored, and each is checksummed against the manifest again as it is copied, so a file changed after verification is never written.
- **Staged first.** After the pre-import backup and under the scheduler's restore hold, `backup.StageFiles` copies every file the restore will write into a directory beside its category's own (same filesystem) and refuses on any failure, leaving the database and every directory untouched. Only then is the database restored, through `RestoreDatabase` as above.
- **Applied per category, each all or nothing.** Custom config, templates and stacks are put in place one category at a time; a category that fails part-way is put back exactly as it was (templates by swapping the directory, custom config and stacks file by file through a journal), and later categories are not attempted, so each category is wholly the archive's or wholly as it was. The apply does not observe a client's disconnect. A failure names the categories restored and left as they were, and the pre-import archive and destinations to go back to; if putting a category back fails too, the error says so and the files as they were are kept in the staging directory it names.
- **Regenerated, then applied to the running pool.** `Handler.RegenerateConfig`, set in `cmd/hoservad` (`wireConfigImport`), runs the strict topology hook (`share.Service.ApplyTopology`, the array-sequence rebuild and `RefreshLive` on the running pool; the same hook the disk-topology jobs run) and `UPSService.Regenerate` (NUT files from the stored settings, and a reload). Both run, under the restore hold and whatever the file apply did, and each failure is reported. An import with no hook configured is refused (501). Each `config.Generator` writer is either regenerated or one whose inputs an import cannot change:

  | Managed file | Inputs | After an import |
  |---|---|---|
  | `smb.conf`, NFS exports, per-share and catch-all pool mount units | shares, array, create policy | regenerated (`ApplyTopology`) |
  | the storage-target units | array disks | rebuilt by the array-sequence rebuild in the same hook |
  | NUT files (`nut.conf`, `ups.conf`, `upsd.users`, `upsmon.conf`) | `ups_config` | regenerated (`UPSService.Regenerate`), removed when the restored database has no UPS |
  | disk mount units, `snapraid.conf` | array disks | not regenerated by an in-place import: `array_disks` equal, or the import is refused; regenerated by a bare-metal restore (`Handler.RegenerateArray`) |
  | `network/interfaces.d/hoserva` | not in the database | not touched |
  | Docker `daemon.json` | the data-root move a user applied | not re-applied: it restarts Docker, and an import never touches a running container |

  Starting containers after a restore is bare-metal step 5, which the bare-metal restore below does not do: it neither touches a running container nor starts one.

The preview writes nothing: no database row, no pre-import archive, no job and no scheduler restore hold, and the staged upload is removed on every path.

**Bare-metal restore** — the important one. `hoserva config import <archive>` on a freshly installed system (the same command as in-place restore; it detects a fresh install and runs this flow):

1. Read the manifest and check compatibility: an archive from an older Hoserva is upgraded by the same schema-migration runner as a normal upgrade (doc 01 §4, D16); an archive from a newer Hoserva is refused
2. Scan attached disks and match against the recorded serials
3. **Show the mapping and require confirmation** — disks may have moved, been replaced, or be absent
4. Restore the DB, regenerate configs, remount the pool (the in-place restore's own steps above: `RestoreDatabase`, `RestoreFiles` and the regeneration hook)
5. Restore stacks and offer to start containers
6. Report anything that could not be restored, explicitly

Step 5's offer to start containers is not part of the restore: the stacks are restored with the files in step 4, and the restore neither touches a running container nor starts one, which needs the compose-stack work (#278).

**Fresh install.** An installation is fresh when it has **no array configured** (`backup.IsFreshInstall`: no `array_disks` row), whatever admin accounts it has, so the same flow runs from `hoserva config import` on a box nobody has set up and from the Restore section after onboarding created an admin (Q28). On a fresh install the in-place refusals for another installation's archive and a different array (409 `archive_other_installation`, 409 `archive_array_mismatch`) do not apply, since another installation's archive is exactly the expected input; on an installation with an array they apply as above, and a `diskMapping` sent to one is refused (409 `disk_mapping_not_applicable`) rather than ignored.

**Reachable before an admin exists, on the socket only.** While no admin account exists the setup gate (`api.SetupGate`) refuses every operation but `/setup/status` and `/setup/admin`. The Unix-socket listener, whose peer is credential-checked (doc 01 §3, Q44), alone also passes `importConfig` and `previewConfigImport` (`api.ConfigImportPaths`); the TCP listener answers them `setup_required` until an admin exists, so no one on the LAN can restore an archive onto a box that is not yet claimed. Every other operation stays gated on both.

**Schema (step 1).** The archive's database is copied to a directory of its own and upgraded there with `store.Runner.Apply`, the runner a daemon start uses, never the archive's own file and never the live database (`backup.StageBareMetal`). A schema newer than the running one is refused (409 `archive_newer_version`) before anything is written; one the runner cannot upgrade is refused as 400 `incompatible_archive`. The preview reports `bareMetal.schemaUpgrade`, or the blocker `archive_newer_version` and no `bareMetal` block.

**Disk mapping (steps 2 and 3).** Each array disk the archive records is matched against `disk.Provider.List`, which reads udev's cache and never opens a device (Q13), by the match GetPool makes for the live array (`backup.MatchAttachedDisk`: `disk.Identity.Matches`, WWN and then serial, and for a weak-identity or by-id-less disk, as in the lab, filesystem UUID and size, Q21). The boot disk is never a candidate. Each recorded disk is then one of:

| State | Meaning |
|---|---|
| `matched` | exactly one attached disk carries its identity, and its filesystem is the recorded one |
| `absent` | no attached disk is it |
| `replaced` | an attached disk holds its filesystem under another identity, or the disk with its identity holds another filesystem |
| `ambiguous` | more than one attached disk matches, a disk and its clone; it is assigned to neither |

`previewConfigImport` shows this as `bareMetal.disks`, each disk by name (role, index, mountpoint and the identity it was recorded with), and `bareMetal.diskMapping`, the mapping to confirm: an entry for each matched disk and none for any other. `hoserva config import --preview` prints both, and `--json` returns the block, from which the mapping is saved to a file for `--disk-mapping-file`. `importConfig` takes the confirmed mapping as its `diskMapping` field (the JSON of the mapping, as a string) and refuses, before anything is written, a fresh-install import without it (409 `disk_mapping_required`), one that is not a mapping (400 `invalid_disk_mapping`), and one that is not exactly the mapping the attached disks give (409 `disk_mapping_stale`): a matched disk left out, on another device, or a disk confirmed that is not matched. The mapping is compared again once the scheduler's restore hold is taken, after the pre-import backup, and the installation is checked to still have no array, so a disk attached, pulled or renumbered in between, or an array created, refuses the restore instead of being restored over. An empty mapping confirms an archive that records no disk, or one none of whose disks is attached.

**What the restore does (step 4).** After the pre-import archive and under the restore hold it prepares the staged database in one transaction (`backup.BareMetal.Apply`), so a failure changes nothing: this installation's own `machine_key_check` and `backup_recipient` rows replace the archive's, since `auth.LoadOrGenerateMachineKey` treats a check value that does not match the key file as a fatal startup error (Q28); each matched disk's `device` is the attached disk's (`UNIQUE(device)` is satisfied through placeholders, and an unmatched disk keeps its recorded device unless a matched disk now has it); and every column sealed under the archive's machine key is cleared, users' TOTP enrolment with it, so the next login enrols again (`backup.sealedColumns`; Q28's bare-metal reading). It then runs the in-place restore's own steps unchanged: the array state kept (`KeepArrayState`), `RestoreDatabase`, the files (`RestoreFiles`), then the disk mount units, `snapraid.conf` and the pool mounts written from the restored array (`Handler.RegenerateArray`, `job.RegenerateArrayMountsFromStore`), and last the configs regenerated and applied (`Handler.RegenerateConfig`). Nothing is formatted or partitioned, no disk is written to before the confirmation, and the flow reads the archive, the databases and the attached-disk list only, never a data disk (Q13).

**Host files the restore takes over (step 4).** The drift manifest that tells `config.Generator` which files it manages (doc 01 §2) sits beside those files under the host's config root, not in `state.db` and not in the archive. The restored `host_config` (Q76) says which of Samba's `smb.conf` and the NFS `exports` the archived installation imported or left, but the fresh OS has its own package-default copies and a manifest that has never heard of them, so without the steps below Q76's refusal of an existing, unimported file would answer every later share change with 409 `unmanaged_config`. They are the restore's own, before anything is written:

- Before the pre-import archive is taken, `config.Generator.PlanHostFiles` compares the decisions in the staged database (`backup.BareMetal.HostFileDecisions`, Samba and NFS rows only) with the host: each file marked `import` that exists here and is not recorded as unmanaged by this host's own manifest is one the restore replaces, because the regeneration that follows writes it. The preview names each one in the `host_files_replaced` note (`previewConfigImport` reads, and writes nothing), so the confirmation covers it.
- The pre-import archive saves each of those files under `host/`, at its path relative to the config root (`backup.CaptureHostFiles`); nothing restores from `host/`, it is there for a user to copy back. A file that cannot be read fails the archive and so the import, before the hold and the database are touched, and with no backup destination enabled, where the pre-import backup writes nothing, the import is refused too (409 `host_files_not_saved`) rather than replace a file with no copy of it.
- After the database and files are restored and before anything is regenerated, `config.Generator.ReconcileHostFiles` records in one atomic manifest write what the plan found: a file marked `import` as imported (its current contents hashed, the file itself not written), so the regeneration writes it, and one marked `leave` as unmanaged, so nothing ever does. A file with no decision, and any file this host's manifest already records (its own user's choice, or one Hoserva wrote), is left as it is. If recording fails the restore reports it with the pre-import archive to go back to, and the file is untouched.
- Only Samba and NFS are covered: they are the files Hoserva writes. An in-place restore does none of this; its host keeps the manifest it has.

**Only matched disks are mounted.** A disk that is not `matched` stays a row of the restored array, with its recorded filesystem UUID, but is unmounted and not adopted: the storage gate (doc 02 §1, Q69) reports the array degraded while it is missing, and nothing mounts until the user acknowledges that or the replace flow (doc 09 §4) adopts a replacement disk. The restore never adds a second way to change the array's topology.

**The report (step 6).** The `200` restore report lists in `notRestored`, besides the stacks' `.env` files: each disk that did not match, by name (kind `disk`, reason `disk_absent`, `disk_replaced` or `disk_ambiguous`), and each secret cleared for having been sealed under the archive's key (kind `database_secret`, reason `sealed_under_other_key`, the table and column with the row it was in). The stacks' `.env` files are restored exactly as in place, from `secrets.age` when the passphrase given or the configured one opens it, since they are plain files the passphrase alone protects. Re-sealing the cleared database secrets from `secrets.age` under this installation's machine key, and adopting the archive's backup recipient and passphrase, is #448's; until then they stay cleared, and the database is one the daemon starts on either way.

This is the "OS is disposable" claim from doc 01 §6 made real, and doc 06 §4 makes it a routine CI test rather than an assumption.

## 2. Appdata backup

### Why it must ship

Cache-only data sits outside parity by design. Without this job, the cache is a single point of failure for every service on the box — and the failure is silent until the SSD dies.

Unraid's community solved this with a third-party plugin that became near-universal. That is strong evidence it belongs in the core rather than left to the user.

### How it works

```
for each container in scope:
  if stop_before_backup:  stop it, record order
archive /mnt/cache/appdata → destination (tar.zst, or per-container archives)
restart stopped containers in reverse order
verify archive
prune per retention
```

### Requirements

**Per-container stop policy.** Databases (Postgres, MariaDB, anything with a SQLite file) must be stopped or quiesced. Stateless containers need not be. Default to stopping, allow per-container opt-out, and **flag known database images automatically** so a user who opts out of stopping Postgres gets told why that is a bad idea.

**Minimise downtime.** Stop → archive → start, with the archive written locally first and uploaded afterwards, so containers are down for the copy and not for a slow upload.

**Per-container archives**, not one monolith. Restoring one broken service should not require unpacking 80 GB.

**Same destination system** as config backup — multi-destination, rclone-backed, verified, and encrypted off-box (Q80).

**Restore is per-container**, with a preview of what will be overwritten and an automatic pre-restore snapshot of the current state.

### Schedule

Weekly by default, plus **automatically before any container update** (doc 04 §6) — the single most valuable moment to have one, and the thing most often missing when someone needs it.

### How it works (#61)

`backup.AppdataService` runs the backup and the restore over the same destinations, encryption and pool-write gate the config backup uses (§1), and over `container.Lifecycle` for the Docker Engine: it never talks to Docker itself, and every stop and start goes through the lifecycle actions.

- **Scope.** A container is in scope when one of its bind mounts, symbolic links resolved, is a directory strictly inside the appdata location (the cache disk's `appdata` directory, the same root container removal deletes under); a mount of the location itself, or of a file, is not appdata. A cache-less array has no appdata location, and the run says so and does nothing. `GET /appdata/backup` lists the containers in scope.
- **Policy.** Each container is stopped and included unless the operator says otherwise, stored per container name in `appdata_backup_containers` (D4) through `PUT /appdata/backup/containers/{name}`. Known database images — the image's last path segment, so `lscr.io/linuxserver/mariadb` and `bitnami/postgresql:16` both match, against a fixed list (Postgres, MariaDB, MySQL, MongoDB, Redis and similar) in `backup.IsDatabaseImage` — carry `databaseImage`, and one that is included but not stopped carries `warning` in the listing and in the `PUT` response, is named in the job output, and is recorded in its archive header. Opting out is allowed; the flag is the mechanism, not a refusal. A file-based database in an unrecognised image is not detected: stopping stays the default for everything.
- **Run.** `POST /appdata/backup` queues an `appdata_backup` job (service class, scoped to the containers it covers so a recreate of one queues behind it), refused with `array_stopped` while the array is stopped or its storage is not ready — with the cache disk unmounted the appdata directories are empty, and an archive of them would report success. In order: every running, to-be-stopped container is stopped (by name, in name order); every included container is archived to a staging directory on the cache disk, next to the appdata location, one archive each; the stopped containers are started again in reverse order; only then is each archive verified and written to the destinations, so a container is down for the copy and not for a slow upload. A container that would not stop is not archived, since its copy would not be consistent; the run continues with the others and fails at the end naming it. Each start has its own deadline that a cancelled job does not cut short. Every container the run attempted to stop is started again on every path, including a cancel and a failed archive.
- **A backup acts on its scope and no further.** The containers a backup covers are resolved once, when it is submitted, and recorded in the job's params (`resolved`) beside what was requested; those names are also its scheduler scope. The run acts on exactly them, however long it waited in the queue: a container installed or included after the submit is not stopped or archived by it, so a recreate or update of that container is never running beside a job that has it down. A resolved container that is gone by the time the run starts, or that was excluded meanwhile (unless the operator named it in the request), is skipped with a line in the job output, and the rest is backed up. A backup job whose params carry no `resolved` fails without touching a container, and the run refuses a request with none: a run never resolves its own scope. A backup that resolved to nothing at submit stays empty and does nothing.
- **Interruption.** Before the first stop the run adds the names it is about to stop to `appdata-backup-stopped.json` in the state directory, keeping any name an earlier run left there, and removes each name it started; one whose start failed, or that an earlier run left stopped, stays in it until the schedule's tick starts it. The file is removed when no name is left. The schedule's minute tick reads that one small file and, while no backup or restore is running in this process and the array is running, starts what it names (`AppdataService.RecoverStopped`) — after a daemon restart mid-backup, an array stop that cut a run short, or an engine that refused a start. It never reads a data disk.
- **Archive.** `hoserva-appdata-<installation>-<container>-<timestamp>[.pre-restore].tar.zst`, with the same age encryption and identity sidecar as a config archive where a destination encrypts (a remote always does). A tar.zst holds a header (container, image, whether it was stopped, the directories archived), one `data/<n>/` tree per directory with modes, owners, times and symbolic links, and a trailer with the file count, byte count and a SHA-256 over the whole tar stream before it: every entry's name, type, mode, owner, times, link target and content, and the header. Verification is one sequential read against the trailer, to the end of the zstd frame so its checksum over the decompressed stream (the trailer included) is checked too; a truncated or corrupted archive has no trailer or fails one of the two. Both checksums are unkeyed and stored in the archive, so they detect accidental corruption and truncation, not a deliberate rewrite by someone who can recompute them. Sockets, devices and pipes are skipped and counted; a file that shrank while its copy was in progress is padded, one that grew is cut at the size it had when its copy began, and both are counted (as is one that vanished), so an archive of a container that was not stopped says how many files changed size. Growth is noticed when the copy of that file ends, and a file rewritten in place at the same size is not detected.
- **Destinations.** Every enabled destination except the boot device's default one (Q40): appdata archives are far larger than config archives and that disk is small. A run fails when any enabled destination could not be written, naming it; the archives already written stay. Unlike a config backup it does not record a success on the destination, so an appdata backup never hides a destination whose config backups have stopped from the stale-destination alert.
- **Retention.** Each destination's daily/weekly/monthly retention, applied per container and only to this installation's archives of that container. The pre-restore snapshots (below) are kept apart: the 5 newest per container survive, and they never take an ordinary backup's tier slot.
- **One at a time, queued.** Every appdata backup and restore, whichever containers it covers, uses the same staging directory (a run clears it when it starts) and the same stopped-container journal (read, changed and written back), so two must never run together. The scheduler enforces this: besides its containers, each `appdata_backup` and `appdata_restore` job's scope holds one shared entry (`backup.AppdataJobResource`), so a second job — a manual backup beside another container's restore, or the weekly backup beside a restore of a container excluded from it — is queued behind the first and runs when it ends, and is never failed for the wait. Previews are not in that entry: they have a staging directory of their own. The service's own lock stays as the backstop for what is not a job: `RecoverStopped` (run on the schedule tick) takes it too and skips the tick when a run holds it, and a backup or restore that finds it held waits for it rather than failing (a run cancelled while it waits does nothing when its turn comes). There is no "busy" error: nothing is refused for contention.
- **Restore.** `POST /appdata/backup/restore` (`confirm: true` required) queues an `appdata_restore` job for one container, one archive on one destination; `GET /appdata/backup/archives` lists what can be restored, and a destination that could not be listed is reported, not read as empty. The job fetches the archive, decrypts it with the onboarding identity and verifies it end to end, and checks that every directory it names is exactly where the backup would have put it — absolute, already resolved, strictly inside the appdata location — before anything is changed. Then, if the container is running, it is stopped, and so is every running container with a bind mount inside the directories being replaced or holding one of them (a transcoder mounting part of a media server's appdata keeps its mount on the tree the swap renames away and deletes, and would write into it). Those containers are resolved when the restore is queued (`AppdataService.RestoreSharers`) and are part of the job's scope, so a recreate of one waits behind the restore; one that shares the archive's directories and is running but was not resolved then refuses the restore before anything is stopped; **a snapshot of the appdata about to be replaced is written to the destinations and the restore refuses, changing nothing, unless at least one of them holds it**; the archive is unpacked next to each live directory, flushed to disk, and swapped in by renames, so a failure while unpacking or swapping leaves the live appdata as it was (a swap that fails part way puts back what it already swapped); and what was stopped is started again on every path, the restored container first. Extraction creates only directories, files and symbolic links, and refuses an entry that would be written outside its tree or through a link the archive itself created. The restore job is not cancellable: a cancel between its steps is the way to leave the appdata half replaced.
- **Restore preview.** `POST /appdata/backup/restore/preview` takes the same container, archive and destination as the restore (no `confirm`, since it changes nothing) and queues an `appdata_restore_preview` job, in the service class scoped to the container like the restore, so the scheduler runs it behind a backup or restore of the same container and beside those of others; it never takes the lock those two share, so a scheduled backup is queued or runs, never refused, while a preview is reading a large remote archive. `GET /appdata/backup/restore/preview/{jobId}` returns the result once the job has succeeded, and says why there is none while it is queued or running (409 `appdata_preview_not_ready`), when it failed, was cancelled or was interrupted (409 `appdata_preview_failed`), or when the result is no longer held (404 `appdata_preview_gone`). The daemon keeps the sixteen newest results in memory only, so a result is gone after a restart and after sixteen newer previews; a preview is cheap to run again and nothing else depends on it. The request is checked like the restore's before the job is queued (array running, the archive's name, the destination, the archive being on it), and the job fetches, decrypts and verifies the archive with the code the restore uses (`fetchVerifiedAppdata`), so it fails with the restore's own error for a corrupt archive, another container's, or a directory outside the appdata location. Per archived directory (named relative to the appdata location, never by its mount path) it compares the archive with the live directory and returns, for each of three groups, a file count, a byte total and a sample of at most 20 paths in path order, relative to the directory: `replaced` (in both; the bytes are the live files that would be lost), `added` (only in the archive; the archive's bytes) and `removed` (only live, which the restore deletes because it swaps the directory as a whole; the live bytes). Directories are not counted, symbolic links and other entries are, and a file is `replaced` whether or not its content differs, since telling would mean reading every live file. It also refuses the entry layouts extraction refuses, by building the tree extraction would build in memory and checking each entry against it: a path leaving its tree, a link type other than a symbolic one, an entry whose place an earlier one already took (a path twice, a directory listed twice, a file where a directory is), and an entry written below a file, below a directory the archive has not listed yet, or through a link that leaves the tree. Files below a link that stays in the tree are listed where extraction puts them. A restore that would fail at unpacking because of its layout is therefore refused before anything is stopped; a disk that fails while unpacking is not predicted. It stops no container and writes nothing under the appdata location; the fetched archive is staged in a directory of its own next to the location, apart from the backup and restore staging so neither clears the other's, and removed when the job ends, on success and failure (one a dead daemon left is removed by the next preview). It walks the live appdata only when asked (Q13), never on a timer. It is cancellable: a cancel stops the fetch, the reading of the archive and the walk of the live directories, but not the decryption or the verification read that follow the fetch, which take no context and run to their end first.
- **Schedule.** The `appdata_backup` schedule is on and weekly (Sunday 04:00) by default, and runs through the daemon's one loop for separately scheduled jobs (`tickOtherJobs`), which claims a window before starting the job, so a restart in the same window cannot start it twice. A schedule saved or seeded mid-week waits for its next window; a window missed while the daemon was down still runs once. With nothing in scope the job succeeds having done nothing. A scheduled or manual backup that fails, or that cannot even be started (the array is stopped), publishes `appdata_backup_failed`.
- **Not built yet.** The automatic pre-update snapshot waits for the container update path (doc 04 §6); there is no per-destination choice of what it takes (`/settings/backup`'s appdata section, #64).

## 3. Pool data backup — what Hoserva does and does not do

**Does not:** implement deduplication, incremental block-level backup, versioning, or cloud sync for bulk data. Those are solved problems with better tools.

**Does:**

- **Be honest.** The docs and the UI state plainly that parity is not a backup — it protects against disk failure, not against deletion, ransomware, corruption, fire, or theft. A surprising number of NAS users believe otherwise, and the `concepts/parity-is-not-backup` and `concepts/what-happens-when-a-disk-dies` pages (doc 05 §7) should say so directly.
- **Ship curated backup containers** in the catalog with pool-aware defaults: Duplicati, restic/Backrest, Kopia, Borgmatic, rclone. Pre-configured to see the pool, store their own config on cache, and not accidentally back up the appdata they live in.
- **Surface backup status** — if a known backup container is installed, show its last-run state on the dashboard. Shallow integration, high value: the common failure is a backup job that silently stopped working months ago.
- **Provide snapshot-friendly primitives.** `snapraid` content and parity give point-in-time recovery for accidental deletion (doc 02 §2) — **but only until the next sync**, which makes the deletion permanent. That is the nightly chain by default, and the threshold guard only holds a sync for *mass* deletions. The guided fix flow (doc 03 §3.5) is the recovery path, and it should be documented as "undelete" — with that time limit stated in the first sentence, not a footnote.

### The stated posture, for the docs

> Hoserva protects you from a disk dying. It does not protect you from you, from ransomware, or from your house burning down. Parity is redundancy, not backup. For anything you cannot replace, keep a copy somewhere else — the Apps catalog has good tools for that, and the Backup guide walks through setting one up.

Saying this clearly costs nothing and prevents the single most damaging category of user disappointment.

## 4. What gets backed up by default on a fresh install

The onboarding flow should end with backups configured, not leave it as an exercise:

| Job | Default | Destination default |
|---|---|---|
| Config backup | **On**, nightly | **Two local destinations** — the boot device (`/var/lib/hoserva/backups`) and a pool path, covering the two separate failure domains in doc 02 §6 — plus a prompt to add an off-box destination (Q40) |
| Appdata backup | **On** once the first container is installed, weekly | Local path on the pool |
| Pre-update appdata snapshot | **On** | Local |
| Restore drill | **On**, monthly | n/a |
| Pool data backup | Off | User's choice, with a pointer to the guide |
| VM backup (Phase 3.5) | Off | Local path on the pool, once enabled |

Defaults that protect people who never open the settings page are worth more than options for people who do.

## 5. VM backup (Phase 3.5, doc 14)

VM vdisks are large files living on cache or array (doc 14 §2), covered by neither config backup (too big, not what it's for) nor appdata backup (scoped to `/mnt/cache/appdata`, not `/mnt/user/domains`). Same reasoning as §2, applied to a different kind of file.

### What ships

- **Domain backup.** On schedule or on demand, `hoserva vm backup <name>` stops the VM, copies its domain XML and vdisk(s) to a destination through the same multi-destination, rclone-backed system as config and appdata backup (§1, §2), verifies, restarts the VM. Live, non-disruptive snapshotting (a libvirt external snapshot while the guest quiesces) is a post-1.0 refinement, not required for Phase 3.5.
- **Not continuous, not incremental.** A full vdisk copy on a schedule — the same deliberately narrow posture as appdata backup's per-container archives (§2), consistent with doc 00 §4's refusal to build general-purpose backup tooling.
- **Snapshots are not backup.** The libvirt/qcow2 internal snapshots doc 03 §11.3 offers are a convenience for undoing a recent change inside the guest — they live on the same disk as the vdisk they snapshot, and are lost with it. Stated plainly in the UI, the same posture as §3's "parity is not backup."

### Schedule

**Off by default** — a full VM image can be large, so enabling this is a deliberate choice, not an assumption. Weekly when enabled, plus automatically before a VM's domain definition changes materially (vCPU/RAM/passthrough edits), the same "back up before the risky moment" pattern as the appdata backup's pre-update snapshot (§2).
