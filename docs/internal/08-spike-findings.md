## Spike 1 — Spindown under mergerfs

**Verdict: the concern is real, but it is not specific to Hoserva. It is a property of union filesystems in general. Proceed, with mitigations — and the acceptance test in doc 06 §6 is now agent-run confirmed (below), not just designed.**

### What mergerfs upstream says

The mergerfs author maintains a wiki page on exactly this, and the answer is blunt: limiting drive spinup through mergerfs alone is not possible, because mergerfs is a proxy rather than a cache — it translates client calls across N filesystems, so a `readdir` runs against all branches and aggregates, and an `open` must scan across branches to find and select the file. Doing otherwise would require a significant rewrite. The recommended approach is to limit spinup at the client level — keeping software from touching the filesystem in the first place.

Confirmed elsewhere by the same author: mergerfs stores nothing of its own on the drives and does not query them on its own; the access pattern depends entirely on what is requesting data and the policy of that request. The OS caches some information, but when the OS asks mergerfs for data it has no choice but to pass the request through. The kernel already caches, and the user controls which parts of mergerfs the kernel may cache; mergerfs does no explicit caching of its own, because keeping caches aligned is non-trivial when mergerfs does not own the underlying data.

A long-standing feature request to have mergerfs maintain a file-index so a read could target a single disk exists — motivated by exactly the Plex/Kodi case, where the application only wants one file and the whole pool gets woken — and it has not been implemented, for the reasons above. The author's position is that something must track where files live, users change things out of band and expect that to work, and any interaction with a drive that the OS has not cached means spinup.

### Why this does not kill the project

**Other union-filesystem NAS systems have the same property.** Unraid's user-share layer (`shfs`), for example, is also a FUSE union over per-disk filesystems, and "my disks won't stay spun down" is a long-running topic in its community forums — from browsing a share spinning up all disks, through reads landing on every array disk every few seconds with no open files, persisting after stopping VMs, containers, and the Docker service, to disks refusing to stay down for more than a few minutes after a manual spindown.

So the honest framing is: **this is not a Hoserva-specific regression. It is a property union-filesystem NAS setups share, and the difference is in how much help the tool gives you.** That reframes R1 from a kill criterion to a feature opportunity.

Practical reports are also more positive than the theory suggests. One user with a mixed 2×16 TB / 2×4 TB mergerfs pool reports that with a reasonable Linux setup and enough RAM (32 GB in their case), the kernel's filesystem cache keeps the other drives from spinning up frequently. Kernel dentry and attribute caching does most of the work in practice, provided nothing is actively walking the tree.

### Implications for the spec

Three changes, none structural:

**1. Create policy default — reconsider.** `epmfs` remains a good general default, but for spindown specifically, a fill-one-disk-at-a-time policy is better: `lfs` (least free space) writes to the branch with the least free space that still has room, filling disks one at a time, which is useful when you want most drives spun down most of the time, at the cost of no balancing. Note the `epmfs` fallback caveat — users report that when the disk holding an existing path hits `minfreespace`, writes fail with ENOSPC rather than falling back to another disk, which the setup wizard must account for when choosing defaults.

Recommendation: keep folder-locality as the default for balance and blast-radius reasons, but ship a **"Quiet mode" preset** in the wizard that sets `lfs` plus tuned cache options, with the tradeoff stated plainly. *(Carried forward as Q11: the default is `mspmfs`, which keeps `epmfs`'s locality but walks up the path instead of failing with ENOSPC — to be confirmed on the pinned mergerfs build in spike S6.)*

**2. Cache the kernel can use.** mergerfs caching options (`cache.files`, `cache.entry`, `cache.attr`, `cache.negative_entry`, `cache.statfs`) are the actual lever. Longer entry and attribute TTLs mean fewer passthrough lookups and fewer wakeups, at the cost of staleness when things change out of band. Hoserva should expose this as a single plain-language setting — *Responsiveness vs. quiet disks* — rather than five opaque TTLs.

**3. The real differentiator: tell the user what woke the disk.** The recurring theme in these community threads is that users cannot find the culprit. Hoserva can make that visible, which few tools do today:

- Track spin-state transitions per disk with timestamps
- Correlate each wake against process-level IO (`fanotify`, or `/proc` IO accounting sampled around the event) to attribute it to a process and, where possible, a container
- Surface it as a **"What woke my disks"** view: disk, time, duration awake, most likely cause
- Common culprits to detect and name explicitly: Plex/Jellyfin library scans, \*arr rescans, the SMART polling loop itself, Samba `recycle`/`vfs` modules, Docker log drivers writing to array paths, `updatedb`/`mlocate` indexing the pool, file indexers on connected Windows clients

**`updatedb` is worth a special mention** — it walks the entire pool nightly and wakes every disk, it is installed by default on Debian, and it is a classic self-inflicted wound. Hoserva should add `/mnt/user` and `/mnt/disk*` to `PRUNEPATHS` automatically on install.

**4. Keep the acceptance test, adjust the target.** Doc 06's criterion (30 minutes standby with shares idle and appdata on cache) stays, but "idle" must be defined as no Samba clients connected and no containers touching pool paths. Measure it, publish the result, and be honest about what breaks it. *(Adopted as Q31; docs 02 and 06 updated.)*

**5. Hoserva must not be its own culprit.** Beyond SMART polling, anything Hoserva runs on a timer that walks the pool defeats all of the above. The one that was hiding in the spec: a live "files changed since last sync" count implies a polled `snapraid diff`, which stats every file. Replaced by a fanotify change journal (Q13, spike S7).

### Agent-run confirmation, 2026-09-15 (S1 acceptance test, doc 06 §6, doc 07 §1)

**Verdict: confirmed, with no exceptions.** Six 30-minute windows — the three scenarios named in issue #2, each at both a short (1 s) and a long (600 s) mergerfs `cache.entry`/`cache.attr`/`cache.negative_entry` setting — every one showed **zero** movement in any of the 17 `/sys/block/<dev>/stat` fields on any array disk, and **zero** `fatrace` events on any array disk, with working, verified attribution throughout (below).

A first attempt at this confirmation (kept in git history, not reproduced here) found one window with a small, non-zero array-disk delta and explained it in prose, but got its own supporting arithmetic wrong: it named `read_sectors`/`read_ticks`/`io_ticks` as the fields that moved, parsed by eye against a `snapshot.sh` comment that listed only 11 of this kernel's 17 `/sys/block/<dev>/stat` fields. Re-parsing the same committed raw snapshot lines field-by-field (now done by `spikes/s1/scripts/stat-delta.sh`, never by eye) showed the actual delta was entirely in `write_ios` (+8), `write_merges` (+1), `write_sectors` (+59 sectors), and `flush_ios` (+6) — a write-side artifact, not a read, and not `io_ticks`. This run replaces that one: it adds a settle gate ahead of the acceptance matrix, characterizes the write-side artifact directly instead of asserting an explanation, and re-runs the full matrix once, end to end, from the corrected and extended scripts — producing every result below in one pass.

**Setup.** Loop-device lab (doc 06 §3), lab id `2-a1`: 1 parity + 3 data disks (1 G XFS each) + 1 cache disk (512 M XFS), mergerfs pool over the 3 data disks. Mount options matched doc 02 §1's table: `category.create=mspmfs,moveonenospc=true,minfreespace=50M,dropcacheonclose=true,cache.files=partial,cache.statfs=0`, plus `cache.entry`/`cache.attr`/`cache.negative_entry` at `1` ("default") or `600` ("raised") seconds. Packages added to the lab container for this spike only — `attr 1:2.5.2-3`, `fatrace 0.18.0-1`, `samba 2:4.22.11+dfsg-0+deb13u1`, `smbclient 2:4.22.11+dfsg-0+deb13u1` (full setup in `spikes/s1/README.md`) — are not part of the standing lab image; a spike is allowed to do this in its own disposable container (`CLAUDE.md`, "Spikes").

**Scenarios**, each run for the full 1800 s, one after another (a single 3-disk array can't serve two scenarios at once without contaminating both scenarios' disk counters):

- **idle** — nothing touches the pool.
- **appdata** — a proxy loop writes one 4 KiB file every 5 s directly to the cache disk's `appdata` directory, standing in for a container's cache-only appdata bind mount (doc 02 §1: cache-only shares have no array branches at all, so this workload never enters the pool's FUSE layer by construction, not just by observation).
- **smb** — the appdata proxy, plus Samba (`smbd`) exporting the pool as a guest share, plus one `smbclient` session held open and genuinely idle (stdin fed from a FIFO, no command sent until `quit` at the very end) for the full window.

**Attribution.** A first attempt used one whole-mount-namespace `fatrace` instance per window, filtered afterward to paths under each array disk's mountpoint. It could not work: this lab container's capability set (`docker-compose.dev.yml` grants `SYS_ADMIN` only) lacks `CAP_DAC_READ_SEARCH`, which `open_by_handle_at(2)` needs to resolve a fanotify file handle back to a path, so every event's path printed as `(deleted)` regardless of what happened — a path-based filter can never match in this lab, confirmed producing zero true positives. The working mechanism instead runs **one `fatrace -c` ("current mount") instance per array disk**, each launched with its working directory on that disk's own mountpoint before `fatrace` starts. `-c` scopes the fanotify mark to the filesystem of the current directory (`FAN_MARK_FILESYSTEM`), so any event a disk's own tracer logs is IO on that disk by construction, attributed by PID and process name (which `fatrace` reports without needing to resolve a path) — no path resolution required.

**Positive control**, run once before the six-window matrix and gating it (`spikes/s1/scripts/positive-control.sh`, `spikes/s1/results/positive-control.log`), now covering both halves of the mechanism:

1. **Direct-disk probe**: a probe file is written, read and deleted directly under `disk2`'s real mountpoint, with all three per-disk tracers running. The probe's four events (`bash`/`cat`, open/write/read/close) appear only in `disk2`'s log; `disk1`'s and `disk3`'s logs are empty for the same window — proving a tracer sees real IO on its own disk and does not see IO on another disk (no cross-contamination between the three `FAN_MARK_FILESYSTEM` scopes).
2. **Pool-routed probe**: a probe file is written and read through the mergerfs pool mount (`$LAB/mnt/user`), not a disk's own mountpoint. mergerfs's `mspmfs` create policy placed it on `disk3` this run; `disk3`'s tracer recorded all six events (open/write/close-write/open/read/close), attributed to the `mergerfs` process by name, and `disk1`'s and `disk2`'s logs stayed empty. A previous attempt's positive control only covered case 1; an independent verifier check in a separate lab confirmed case 2 held, but the recorded evidence didn't demonstrate it — this run's positive control now does.

`run-window.sh` also clears each disk's log/err file before starting its tracer and checks the tracer's exit status (not merely whether it printed anything to stderr — this lab's inability to resolve paths makes `open_by_handle_at: Operation not permitted` an expected, harmless line on every logged event); a tracer that exits non-zero fails the window loudly rather than reporting a silent `(none)`.

**Settle gate**, run once after the positive control and before the six-window matrix (`spikes/s1/scripts/settle-gate.sh`, `spikes/s1/results/settle-gate.log`): an explicit `sync`, then disk1-disk3's `/sys/block/<dev>/stat` sampled every 5 s until every array disk has been unchanged for 180 s (3 minutes), or the gate fails after 900 s. This exists because the positive control's own probe writes (above) leave `disk2` and `disk3` with pending writeback that does not appear immediately, even after `sync` — the gate makes the acceptance matrix start only once that has genuinely finished, rather than assuming it has. This run's gate needed 230 s total: two further small write-side deltas on `disk2` and `disk3` (`write_ios` +2, `write_sectors` +3, `flush_ios` +2 each, roughly 30 s apart — T+20s and T+50s after the gate's own `sync`) before going fully quiet for the required 180 s. No array disk moved again for the rest of the ~3-hour run (below) — the gate's 180 s requirement, chosen before this run as "at least 3 minutes" per issue #2, turned out to be roughly 3.5x the margin this run actually needed.

**Trailing-write characterization**, run once before the positive control, on `disk1` alone, with no other array disk yet touched (`spikes/s1/scripts/trailing-write-characterization.sh`, `spikes/s1/results/trailing-write-characterization.log`): after one `sync` for a clean baseline, a create+write+unlink probe directly on `disk1`'s own mountpoint, then `disk1`'s stat line sampled every 5 s for 6 minutes with **no further sync**, to see when and by how much deferred writeback moves the counters on its own. Result: `read_ios` (+3) and `read_sectors` (+48 sectors) appeared already at the first 5 s sample and never moved again — a synchronous, cold-cache metadata read from the probe's own `open()`/`create()` on a filesystem nothing had touched since `mkfs`/mount, not a deferred effect. The write side arrived in two further steps, each roughly 30 s apart: `write_ios`/`write_sectors`/`flush_ios` were `+5`/`+55`/`+2` at T+5s, `+7`/`+58`/`+4` by T+35s, and reached their final `+9`/`+61`/`+6` (plus `write_merges` +1) by T+65s — then stayed exactly there through T+360s, the full 6 minutes. The container's own read-only sysctls: `fs.xfs.xfssyncd_centisecs=3000` (30 s), `vm.dirty_expire_centisecs=3000` (30 s), `vm.dirty_writeback_centisecs=1500` (15 s) — the ~30 s spacing between the write-side steps matches XFS's own periodic background sync interval, not a single writeback pass. The final write-side magnitude (`write_ios` +9, `write_sectors` +61, `flush_ios` +6) is the same order as the miscited attempt's original `disk2` delta once corrected (`write_ios` +8, `write_sectors` +59, `flush_ios` +6, see above) — close enough (disk2's probe was a warm-cache write, without the cold-cache read component disk1 shows here) to support deferred XFS background sync of a just-completed write as the mechanism, now with measured timing and magnitude behind it rather than an assumption. This is a measured finding, not a general claim: it describes this lab's XFS-on-loop-device behavior at these sysctl values, and Q31's acceptance procedure now states explicitly that the idle window must start only after array disks have settled, per this measurement.

**Results** (every window ran exactly 1800 s; full logs in `spikes/s1/results/`, per-disk fatrace logs in `spikes/s1/results/fatrace/`, every delta computed by `spikes/s1/scripts/window-delta.sh <log>`, never by eye):

| Scenario | Cache TTL | Array-disk `/sys/block/<dev>/stat` (disk1-disk3, BEFORE vs. AFTER) | Cache-disk write IOs (delta) | `fatrace` events on any array disk |
|---|---|---|---|---|
| idle | default (1s) | no field changed on disk1, disk2 or disk3 | 0 | 0 |
| idle | raised (600s) | no field changed on disk1, disk2 or disk3 | 8 (trailing writeback of `smb-default`'s own cache writes, see below) | 0 |
| appdata | default (1s) | no field changed on disk1, disk2 or disk3 | 551 | 0 |
| appdata | raised (600s) | no field changed on disk1, disk2 or disk3 | 669 | 0 |
| smb | default (1s) | no field changed on disk1, disk2 or disk3 | 535 | 0 |
| smb | raised (600s) | no field changed on disk1, disk2 or disk3 | 667 | 0 |

"No field changed" is `stat-delta.sh`'s literal output: every one of the 17 `/sys/block/<dev>/stat` fields matched byte-for-byte between the window's `BEFORE` and `AFTER` snapshot, for every array disk, in every window — the acceptance bar issue #2 states ("counters stay flat for ≥ 30 minutes") is met exactly as written, not approximately. `run-window.sh` now runs an explicit `sync` immediately before its `BEFORE` snapshot (not only once, before the whole matrix) — the fix the settle gate and characterization above establish is necessary, applied everywhere a window could otherwise start mid-writeback. The cache disk's write-IO counters moved by a comparable, substantial amount in every `appdata`/`smb` window regardless of cache-TTL setting (hundreds of write IOs vs. single digits or zero in `idle`), confirming the proxy workload genuinely ran each time — this is what makes the array disks' zero-delta result meaningful rather than an artifact of nothing happening at all. `idle-raised`'s own small cache-disk delta (`write_ios` +8, `write_sectors` +63, `flush_ios` +4) is the same deferred-writeback pattern as above, this time on the cache disk, trailing from `smb-default`'s heavy cache writes in the immediately preceding window — the cache disk is not part of the acceptance criterion, and this delta does not touch any array disk (confirmed by that window's own flat array-disk row). Every array-disk `fatrace` log and its matching `.err` file is empty in every one of the six windows (`spikes/s1/results/fatrace/*-disk[123].log`), and the positive control (above) confirms that an empty log means "no IO", not "the tracer wasn't watching".

**Why this run has no exception where the previous one did.** The previous attempt's positive control ran immediately before `idle-default`, with no settle gate between them, so `idle-default`'s `BEFORE` snapshot was taken while the probe's deferred writeback was still in flight. This run's characterization and positive control both run — and settle — *before* the matrix starts, and every window also `sync`s immediately before its own `BEFORE` snapshot. Incidentally, the characterization (on `disk1`) and the positive control (on `disk2` and `disk3`) between them touch every array disk once before the matrix begins, which is also why no array disk in this run shows the cold-cache read effect the characterization found on `disk1`'s very first-ever operation — by the time `idle-default` starts, every array disk's metadata is already warm.

**The raised-timeout question, answered as measured, not assumed.** An earlier draft of the test plan dropped `idle:raised` and `appdata:raised` on the reasoning that a mergerfs-FUSE-level cache-TTL setting cannot matter to a workload that never queries the FUSE layer. The maintainer correctly overruled that for this issue — narrowing an explicit acceptance bar ("each with default and raised cache.* timeouts") is a maintainer call, not an executor one — and the six-window run above is the actual measurement: **raised timeouts made no observable difference in any of the three scenarios.** For `idle`/`appdata` this matches the architectural reasoning (nothing ever asks the pool for anything, so there is nothing for a cache TTL to serve stale-vs-fresh). For `smb`, the reason is different and more interesting: an idle, connected, non-browsing `smbclient` session generated **no periodic traffic at all** — `smbd`'s log shows the one-time startup banner and a one-time `passdb.tdb` version conversion, then nothing for the remaining ~30 minutes, in both the default and raised window. The hypothesis that `smbd`'s own housekeeping (oplock breaks, change-notify polling) would periodically walk the pool tree was not observed in this minimal Samba 4.22 config with a single idle, non-browsing client. That is a real result, not a proxy artifact — but it is also a narrower test than "a real SMB client on a real desktop" (see residual risk).

**Recommendation on "Quiet mode" timeouts (doc 02 §1's `cache.entry`/`cache.attr`/`cache.negative_entry` row).** This run did not find a scenario where raising the TTL from 1 s to 600 s bought anything — the default already kept every tested scenario silent — but it also tested none of the scenarios doc 08's own "common culprits" list names (directory browsing, an indexer, `updatedb`, multiple clients), which are precisely the cases a longer TTL should help with, since those genuinely re-query the tree. Recommendation: ship the "Quiet mode" preset at `cache.entry=cache.attr=cache.negative_entry=600` (10 minutes) as planned, stating the staleness tradeoff plainly in the wizard — a file added or removed by another process can take up to 10 minutes to show up in a client's cached directory listing — rather than concluding from this run that the setting is unnecessary. The defaults (short TTLs) already suffice for the scenarios tested here; the raised setting remains a recommendation for the untested culprits, not a confirmed necessity.

**Residual risk**, beyond the standing "firmware/controller wakes with no host IO" (doc 06 §6): everything this run's proxies don't cover, plus what the settle gate and characterization narrow but do not eliminate. No real Docker container (the lab has no Docker-in-Docker, doc 06 §3) — the appdata proxy is a shell loop writing directly to the cache disk, not a container's own filesystem/image-pull/log-driver traffic. One idle SMB client, not a real desktop's directory browsing, thumbnail generation, search indexer (Windows Search, Spotlight) or antivirus real-time scanner — doc 08's own culprit list names several of these and none were exercised. No NFS client at all. No concurrent multi-client load. No `updatedb`/`mlocate` run against the pool. No SMART polling (tracked separately, doc 06 §6's own table row). **Fanotify-based attribution cannot see writeback-only IO** — deferred flush of an already-completed file operation reaches the block device with no corresponding file-level event, confirmed and timed by this run's characterization (up to ~65 s after the triggering operation, on this lab's XFS/loop-device setup with 30 s `xfssyncd_centisecs`) — so a real "what woke my disk" feature (Q32) built purely on fanotify would misreport a deferred flush as unattributed IO; a production implementation needs either a settle/sync discipline around measurement windows (as this run now applies) or a complementary block-layer signal for this case. The ~65 s settling time and the 30 s XFS sync-thread cadence behind it are measured on loop devices in this lab, not on real disks with real firmware and real controllers — a real disk's own settling time before it is safe to call "quiet" for spindown purposes is not established by this run. This run confirms the zero-organic-IO property holds for the three scenarios and both cache settings issue #2 asked for, exactly as stated (no exceptions, no explained-away deltas); it does not confirm spindown survives everything doc 08 names as a risk.

### Agent-run confirmation, 2026-09-18 (L3 SMART-poll IO-neutrality, issue #33)

**Verdict: confirmed for what L3 can actually exercise today — and that turns out to be narrower than doc 06 §6's table row implied, for a structural reason rather than a Hoserva one.** `scripts/vm/spindown-check.sh` (wired into `make vm-suite` as steps 9 and 10 of `scripts/vm/run-l3-suite.sh`, so it now runs nightly per `.github/workflows/nightly-l3.yml`) issues the exact `smartctl -j -n standby -a <dev>` invocation `internal/disk`'s `LinuxProvider.SMART` makes, repeated every 60 s across a full 1800 s (30-minute, Q31's own bar) window against every array disk. It uses Spike 1's own settle gate from above — an explicit `sync`, then every array disk's `/sys/block/<dev>/stat` unchanged for 180 s (the cache disk is not watched, as it is not part of the acceptance criterion), sampled every 5 s, failing after 900 s — immediately before the `BEFORE` snapshot. No `sync` runs inside the window. Instead, before the `AFTER` snapshot it waits `dirty_expire_centisecs` + `dirty_writeback_centisecs` + `xfssyncd_centisecs` (65 s at the guest's defaults), so a write dirtied late in the window still reaches the disk. On any non-zero exit it prints the failing command and both snapshots, and it writes everything to stdout. Why (issue #347): a `block_bio_queue` tracepoint in the guest showed the check's own `sync` sending an empty flush (`FWS 0 + 0`) to every mounted ext4 data disk even with nothing dirty — `write_ios` and `flush_ios` +1, no sectors, the XFS parity disk unmoved — and `run-l3-suite.sh`'s stderr no longer reaches the log by this step, so a failure written there was lost.

**Setup.** L3 VM harness (doc 06 §4), lab id `33-a1`: the standard 7-array-disk topology (`scripts/vm/create-vm.sh`) — `parity`, `disk1`-`disk5`, `cache` — all attached `bus='virtio'`. `smartmontools` is not a dependency of the `hoserva` package (`packaging/debian/control`'s `Depends:` line has no smartmontools, hdparm or util-linux beyond `adduser` — see "Findings outside this issue" in the issue #33 execution report), so `spindown-check.sh` installs it itself over SSH the same way `deploy.sh` installs the `.deb`, and explicitly disables the `smartmontools.service` (`smartd`) unit the package enables by default — otherwise smartd's own periodic scan, one of this doc's own named "common culprits" (§1 above), would contaminate the very measurement this script is making.

**Result, validated against a live VM (60 s window, 15 s poll interval, for iteration speed) and once more with an injected write to prove the failure path is real, not assumed:** every one of `smartctl`'s invocations against every array disk (`vdb`-`vdg`) returned **exit 1, `"Unable to detect device type"`** — `/dev/vdN`'s virtio-blk transport has no ATA or NVMe protocol underneath for `smartctl` to query, so it never gets real SMART telemetry, on any array disk, regardless of the `-n standby` flag. **Despite that, `/sys/block/<dev>/stat` stayed byte-for-byte identical, on every array disk, across the whole window** — confirming the property Q31/doc 06 §6 actually need ("no read IO"), for the literal command the poller issues, even though the command itself cannot succeed in this harness. A second run with a `dd` write injected directly against one array disk mid-window (`/dev/vdc`, 4 KiB, `conv=fsync`) was correctly detected and reported as a `FAIL` with the moved `/sys/block/vdc/stat` fields printed — proof the check does not just always pass.

**What this narrows, and why it is a harness gap, not a product one.** QEMU/libvirt do not synthesize ATA/NVMe SMART data for a qcow2-backed virtual disk regardless of bus (`virtio`, `sata`, `ide`, `scsi` would all show the same "Unable to detect device type" symptom, since none of them make the backing file a real ATA or NVMe device) — SMART is a property of the physical media and its controller firmware, which a disk image file has none of. So **doc 06 §6's "In L3, assert the poller issues only standby-aware queries and causes no read IO" is confirmed exactly as far as "causes no read IO"; "issues only standby-aware queries" is true by construction (the script only ever issues the `-n standby` argv), not independently observed from a real disk's own standby response** — there is no way, in this or any qcow2-backed L3 harness, to observe a real disk actually honoring or ignoring `-n standby`. That is the residual risk doc 06 §6's own table already names ("Firmware that spins up on a SMART query despite `-n standby`") — this run establishes that L3 cannot narrow it at all, not even partially; only real hardware can, and D20 rules that out for any agent.

**What this issue could not yet reach, honestly recorded rather than stretched.** The acceptance criteria's first bullet asks for the 30-minute flat-counter property "with... SMART polling and the change journal running" — as of this run, neither is wired into `hoservad` on a timer: `internal/disk`'s SMART poller and `internal/parity`'s change journal both exist as Go packages with L1/L2 coverage (issue #24), but nothing in `cmd/hoservad/main.go` calls either one periodically, and there is no array/pool operation in `api/openapi.yaml` yet for a VM-level test to configure a real pool through (the same gap `run-l3-suite.sh`'s own "array setup" step already names). `spindown-check.sh` works around the missing scheduler by looping the poller's own command directly for the window — a faithful stand-in for "the SMART poller runs and causes no IO", but not proof that `hoservad`'s own (not-yet-built) scheduler does the same, and not a pool for the change journal to watch. ## Spike 2 — Unraid disk adoption

**Verdict: confirmed — both from public research and now agent-run in the lab, 2026-09-16. This works, and it is well-established outside the Unraid ecosystem.**

The strongest confirmation comes from professional data recovery practice, where mounting Unraid disks without Unraid is routine work:

- For each healthy data disk, the XFS or btrfs filesystem is mounted directly and files extracted — unlike RAID recovery, no array reassembly is needed for disks that read cleanly, and each disk's share directories are catalogued and merged into a unified recovery set.
- The USB flash drive is not needed to recover data: each data disk is self-contained, the individual filesystems are mounted, and shares are reassembled from the per-disk directory structures. A dead Unraid stick is a configuration loss, not a data loss.
- Even after a parity rebuild onto wrong assignments — where the parity data itself is destroyed — every individual data disk still contains its original XFS or btrfs filesystem and is extracted directly.

That is precisely the Hoserva import model, described by a third party as standard practice. It also confirms the two secondary assumptions in doc 05: shares are reconstructable purely from per-disk directory structure, and the flash drive carries configuration only.

Supporting details from Unraid's own documentation: XFS is described as generally the best choice for array drives, with EXT4 as a solid traditional alternative, while ZFS and BTRFS are positioned for cache pools and multi-device setups — so the XFS-majority assumption holds for the array specifically. And Unraid identifies disks by serial number and size rather than by SATA port, so drives can be moved between ports without affecting assignments, which validates the serial-based mapping in doc 05 §4 step 7: the serials Hoserva matches on are the same identifiers Unraid itself uses.

### Implications for the spec

- **The primary migration path is sound.** Doc 05's technical basis is confirmed rather than assumed.
- **Filesystem repair belongs in the pre-flight.** Since recovery practice leans on `xfs_repair`, the migration scan should run `xfs_repair -n` (dry run) on each disk and refuse to adopt a filesystem that reports errors. Adopting a subtly corrupt filesystem into a new pool and then computing parity over it would bake the corruption in. *(Adopted for every supported filesystem — doc 05 §3, Q23.)*
- **Encryption is a real complication, per Unraid's own warning** that encrypted drives can pose challenges for recovery if corruption occurs and that encryption complicates data recovery if something goes wrong. Keep LUKS arrays out of v1 or behind an explicit "advanced, you understand the risks" path. *(Adopted: detect and refuse in v1 — Q22.)*
- **ZFS-formatted array disks (Unraid 6.12+) are now plausible enough to need a stated position.** Recommendation: detect and refuse in v1 with a clear message, rather than half-supporting. *(Adopted — Q23.)*

**The central finding: a plain `-o ro` mount is not byte-for-byte silent, even on a cleanly-unmounted filesystem.** `spikes/s2/scripts/check-fixture.sh` brackets every mount with a whole-partition byte-level snapshot (`s2_snapshot_bytes`, `lib.sh`) taken immediately before and after. Where the two snapshots differ, `cmp -l` (`s2_byte_diff_ranges`) counts every differing byte and reports the contiguous offset ranges, which are then classified (`s2_classify_ranges`) against the disk's own superblock location (always byte offset 0) and its internal log's real byte offset, read once, read-only, straight from the superblock via `xfs_db -r` (`s2_xfs_log_geometry` — note this converts the log's starting fsblock to a byte offset with xfs_db's own `convert fsb ... daddr`, not by hand-multiplying `logstart * blocksize`, because XFS encodes an internal `sb_logstart` as an AG-relative fsblock number whenever the AG size is rounded up to a power of two for addressing, which it is on every fixture disk this spike builds — hand-multiplying silently produces a wrong, too-large offset). This run found that `mount -t xfs -o ro` — with no write attempted through it, on a disk `build-fixture.sh` had already unmounted cleanly, and with `xfs_repair -n` reporting clean both before and after — rewrote **4390, 4395 and 4387 bytes** on `disk1`, `disk2` and `disk3` respectively, and **every one of those bytes falls inside the primary superblock's first sector (offset 0-511) or the internal log region** (offset 167784448-234893311 on every fixture disk, since all three are built identically — `logstart` block 65543, `logblocks` 16384, `blocksize` 4096, `sectsize` 512, per `xfs_db -r -c 'sb 0' -c print`). This byte count is a property of this run, this kernel and this specific 320 MiB fixture layout, not a fixed constant — re-running `check-fixture.sh` reproduces the qualitative result (superblock + log only, never elsewhere, on a cleanly-unmounted disk) but not necessarily this exact count; the committed `spikes/s2/results/check-fixture.log` is this run's own raw `cmp -l`-derived ranges, one line per range, for all three disks. `mount -t xfs -o ro,norecovery` left every disk's raw bytes **byte-for-byte identical** (0 differing bytes) across a mount plus a full read of every file. Every mount this script performs from that point on — every per-disk check and the mergerfs union itself — uses `norecovery`. This is recorded as a general, measured XFS/Linux mount-semantics fact (not Unraid-specific): on this kernel, a read-only mount without `norecovery` still executes log-recovery bookkeeping that writes to the device, so Hoserva's adoption path must never mount a source disk read-only without it.

**A lab-environment pitfall found and fixed while building this, not Unraid-specific but directly relevant to any future test environment without a real init system:** this container has no `udevd`, so nothing invalidates `blkid`'s persistent cache (`/run/blkid/blkid.tab`) when a recycled `/dev/loopN`'s backing image changes. **Controls** (`spikes/s2/scripts/negative-controls.sh`, `spikes/s2/results/negative-controls.log`), proving the checking mechanisms themselves can fail, not just that they happened to pass:

**The dirty-log case** (`spikes/s2/scripts/dirty-log.sh`, `spikes/s2/results/dirty-log.log`) — the case `build-fixture.sh`'s cleanly-stopped disks don't cover: a disk pulled while the array was still started, or after a power loss, rather than after a clean array stop (docs.unraid.net again: only *stopping* the array unmounts disks). A fourth, disposable disk (never one of the three verified above) is written to (two files, one `sync`ed, one left in flight) and then crashed with `xfs_io -x -c shutdown` while still mounted — the same mechanism `xfstests` itself uses to simulate an unclean shutdown of a real, in-use filesystem without touching a real device or fabricating corruption by hand. Each mount variant below was tried against its own **fresh copy** of the crashed image, because the first finding (below) meant testing them against a shared image would have silently contaminated the second variant's result:

- `xfs_repair -n` on the freshly crashed disk: **exit 1**, with an explicit `ALERT: The filesystem has valuable metadata changes in a log which is being ignored because the -n option was used. Expect spurious inconsistencies which may be resolved by first mounting the filesystem to replay the log.` — a clear, scriptable "refuse to adopt without recovering it first" signal for doc 05 §3's existing pre-flight rule.
- `mount -t xfs -o ro` (no `norecovery`) against a fresh copy: succeeded, and **replayed the log** — the two pre-crash `sync`ed files reappeared — but the partition's raw bytes changed doing it (confirmed by whole-device byte snapshot before/after, same `cmp -l`-backed mechanism as the clean-log finding above, `spikes/s2/results/dirty-log.log`: 4399 differing bytes), and `xfs_repair -n` reported clean immediately afterward. A plain `ro` mount silently repairs a dirty log via a write, whether or not the disk actually needed repairing. Unlike the clean-log case above, this replay's writes are **not confined to the superblock and log region** — some of the 4399 bytes fall outside both (a real transaction replay also writes its committed changes to their permanent on-disk locations, e.g. freespace and inode metadata, not only the log it replayed from), consistent with a plain `ro` mount doing genuine log-recovery work, not just touching bookkeeping fields.
- `mount -t xfs -o ro,norecovery` against another fresh copy: succeeded, left the device's raw bytes **completely unchanged** — but showed an **empty directory**, not the two files a `sync` had already made durable before the crash. The file written *after* the last `sync` never appeared in either variant, confirming it genuinely wasn't durable at crash time.

**Why the norecovery result is more than a corruption-avoidance detail.** XFS's delayed-logging model can make a transaction durable — it survives a crash, because it's recorded in the on-disk log — before that transaction is *checkpointed* into its permanent on-disk structures. `norecovery` skips checkpointing the log, so it can hide files that were genuinely, successfully synced before the crash, not only ones that were legitimately lost. Doc 05 §3's existing rule ("`xfs_repair -n` not clean → refuse to adopt that disk") is the right default, and this run is exactly why: a disk in this state is not simply "safe to mount read-only anyway", because `norecovery` — the option that makes read-only genuinely read-only — is also the option that can make Hoserva's own file-count and checksum baseline wrong by omission. What this run does *not* settle is whether "refuse" should stay unconditional: the same disk, once its log was replayed via a normal mount, came back with all pre-crash-synced data intact, which is a much smaller and better-understood operation than a real `xfs_repair` repair pass. Whether the pre-flight should offer a guided, explicit-consent "replay this disk's log first" step distinct from the "refuse" default — and how it is worded so the user understands it writes to their source disk before Hoserva has adopted anything — is a product decision for a Phase 3 migration issue, not something this spike is scoped or positioned to settle.

### Residual risk

- **Scale.** This spike proves adoption end to end on 320 MiB loop devices with 11 files; a real 8–24 TB array with millions of inodes is untested for mount time, `xfs_repair -n` wall-clock, or sha256-verification throughput.

- **ext4 and single-device btrfs data disks** (Q23) are not built or checked by this spike — only XFS.
- **VM/`libvirt.img` adoption** (Q55) is confirmed by source-reading here, not by building or adopting an actual VM fixture — that is spike S11's job (doc 14 §5).
- **The dirty-log/`norecovery` timing finding** is measured on this lab's XFS-on-loop-device setup and this container's IO/writeback behaviour; a real disk's own checkpoint timing before a crash-consistent transaction is safely visible without recovery is not established here.
- **LUKS/ZFS refusal detection** (Q22/Q23) is not built or exercised by this spike. One useful, sourced implementation detail for whoever does build it: `unraid/webgui`'s `DiskSettings.page` shows `defaultFsType` combining encryption with the base filesystem as a `luks:<fs>` value (e.g. `luks:xfs`, `luks:zfs`) rather than a separate boolean field — detection logic needs to parse that prefix, not assume a distinct "encrypted" flag exists alongside the filesystem type.

Every "byte-for-byte identical" claim above is a `diff -u` between two full-array sha256 manifests, both committed and both empty-diff (`spikes/s5/results/d2-reconstruction.diff`, `dual-reconstruction.diff` — both 0 bytes). The sha256 primitive itself is controlled separately: a plain single-byte flip in a throwaway file, checked to actually change the hash, before any of the above is trusted (`spikes/s5/results/run-all.log`, step 4's first control).

**The headline finding: SnapRAID cannot read any data disk's UUID in this lab, at all, ever.** Every `sync`, `diff`, `scrub` and `fix` in the whole run logged `WARNING! UUID is unsupported for disks: 'd1', 'd2', 'd3'. Not using inodes to detect move operations.` (16 occurrences in the one committed `run-all.log`). Reading SnapRAID's own source (`../reference/snapraid/cmdline/unix.c`, `devuuid`/`devuuid_dev`/`devuuid_blkid`) shows its only Linux UUID mechanism is enumerating `/dev/disk/by-uuid`, with a `libblkid`-based fallback gated behind a `HAVE_BLKID` compile flag — and Debian's `snapraid 12.4-1` binary is not linked against `libblkid` at all (`ldd`, `spikes/s5/results/versions.log`), so that fallback does not exist in this build. `/dev/disk/by-uuid` itself does not exist in the lab container (confirmed: `ls /dev/disk` → *No such file or directory*), because nothing runs `udevd` here — the same root cause doc 08 S2 already found for `blkid`'s stale cache, now shown to block SnapRAID's own UUID path unconditionally, not just when a loop device number is reused. This is not a version, config or package-choice problem: `/dev/disk/by-uuid` is populated by a running udev daemon reacting to live device events, which a non-privileged, non-init container (Q45's own narrowed device set) structurally cannot provide, on this host or any other.

**Two measured consequences, each with its own covering layer:**

1. **Intra-disk moves are never classified as `moved`** — an already-synced file `mv`'d to a different directory on the same disk, preserving its inode and mtime exactly as snapraid.txt §5.5 describes for a "moved" file, was reported as `remove`+`copy` instead (`spikes/s5/results/diff-exercises.log`). Functionally harmless in this run — `sync` still picks it up correctly, and `copied` reuses the existing hash rather than rehashing the whole file — but it is a real, measured difference, and this lab is structurally unable to exercise `moved`'s "zero parity recompute" fast path (§5.6). **Covering layer: L3** — a real VM with a full init system and a running `udevd`.
2. **The `-U`/`--force-uuid` disk-identity guard is never actually exercised.** snapraid.txt §6 describes it as detecting "when your disks are mounted in the wrong mount points" by comparing each disk's previously-recorded UUID against what's currently mounted there. Because UUID is never tracked at all in this lab, both reconstruction steps swap a data disk's entire filesystem for a brand-new one at the same mount point and `fix`/`sync` proceed with no complaint — the *correct* outcome for a disk-replacement scenario, but not evidence the guard itself works, only that it never ran (there was nothing for it to compare against). **Covering layer: L3** — the guard's actual trigger (a disk's UUID no longer matching what SnapRAID last recorded for that mount point, e.g. two data disks' mount points swapped by mistake) needs a real UUID source to test at all.

**A related, general (not loop-device-specific) finding: doc 06 §3's own corruption-injection example is a filesystem-integrity risk on a disk this small, not just a SnapRAID-scope one.** Its blind `dd bs=1M seek=100 count=10` was never actually run against a live mount by this spike — `spikes/s5/scripts/04-scrub-and-fix.sh` uses `xfs_bmap -v` to find a target file's exact physical block range first (`spikes/s5/results/xfs_bmap-corrupt-target.log`) and corrupts 500,000 bytes at a computed offset safely inside that file's own extent. On this run's 2 GiB data disks, doc 06 §3's own blind offset (in the first ~110 MB) risks landing on XFS's superblock or an early allocation-group header rather than inside a file, producing a filesystem-corruption test rather than the silent-bit-rot test scrub is actually for — recorded as a doc 06 §3 update. A related, general Linux fact found in the same step: corrupting a device directly underneath a live mount risks the next read being served from a still-cached clean page rather than the now-corrupted on-disk bytes; this run unmounts, corrupts the loop device, and remounts before reading again, specifically to avoid a false pass.

**Two usage details found empirically, general SnapRAID behaviour rather than loop-device-specific:** `fix -f <path>` requires a leading `/` (a bare relative path is refused outright, with the exact fix named in the error text); adding a second parity level to a config that already has data requires `snapraid --force-full sync` (a plain `sync` refuses and names the fix itself in its output). Neither is stated plainly by the manual's own worked examples (§4.3, §7.2).

**Q45 confirmed, with this addition.** The loop-device lab remains the right dev-workflow foundation — every operation doc 02 §2's table lists behaves as documented, including full reconstruction under both single and dual parity — but Q45's entry now names the one thing it cannot exercise (disk-UUID-dependent behaviour) rather than implying full fidelity.

### Residual risk

- **UUID-dependent behaviour** (moved-file fast-path classification, the `-U`/`--force-uuid` guard) is untested by any loop-device lab run and requires L3 (doc 06 §4) or a public-beta report to confirm.
- **Scale.** This run's disks are 2 GiB with ~16 small files; a real multi-TB array's `sync`/`scrub`/`fix` wall-clock, memory use and the block-layout effects of a much larger `blocksize`-relative file-size distribution are untested.
- **Real disk failure semantics** (a genuinely failing sector's IO error timing and pattern, SMART-correlated pre-failure behaviour) are not something a clean loop-device detach can show — doc 06 §6's own standing residual-risk table already covers this class of gap generically; this spike adds nothing new to it beyond confirming SnapRAID's own reconstruction logic is correct given a clean failure signal.
- **ext4/btrfs data disks** are not exercised — every disk in this run is XFS, matching doc 02 §2's own parity-disk requirement and Q20's XFS default, but SnapRAID itself supports ext4/btrfs data disks and this spike says nothing about them.

### Remaining hands-on work

Confirming the two UUID-dependent behaviours above once the L3 VM harness exists (doc 06 §4, currently blocked on `scripts/vm/` and the `vm-*` targets not existing yet — CLAUDE.md); a larger-scale run once realistic array sizes matter for Phase 1's own soak test (doc 06 §6).

## Spike 6 — Per-share mergerfs mount topology

**Verdict: confirmed, agent-run in the lab, 2026-09-16. Doc 02 §1 / Q12's per-share topology stands; the two-mount tiered fallback (Q12, R12) is not adopted.** A catch-all plus a dozen per-share mounts (four each of cache-then-move, cache-only, array-only) mount and unmount cleanly in dependency order; `mspmfs` falls back to the parent path exactly as documented on mergerfs 2.40.2, while `epmfs` — changed only in that one option, on the identical branches and fill state — returns ENOSPC; `NC` branches stay readable while new files land on cache; a stray top-level write lands on a data disk, never the boot device; the twelve-share RSS cost is well inside R12's own bar, and a counterbalanced, warmed-up throughput comparison shows no relative-throughput cost in this run either (−0.01% by median, comfortably under R12's 10% bar, order-effect Pearson r = −0.090, close to zero), though the order-effect check is named as an ongoing measurement caveat regardless of this run's own reading, not hidden; and killing one share's own mergerfs process fails safely rather than silently exposing the array beneath it. Full scripts, raw output and a step-by-step account: `spikes/s6/`.

**Setup.** Loop-device lab (doc 06 §3), lab id `7-a1`, `make lab-up`'s own defaults (3×1 GiB data disks, 1 GiB parity, 512 MiB cache, `minfreespace=50M`) — no override needed. `mergerfs 2.40.2-5` (`dpkg-query -W`, doc 08 S9's own lesson — never `--version`), already in the base lab image, nothing extra installed. Every mergerfs instance launched in the foreground (`-f`) as a backgrounded shell job (`cmd & pid=$!`) — the exact pattern the mergerfs wiki's own systemd unit uses (reference checkout `man/mergerfs.1`, "systemd mount": `Type=simple`, `ExecStart=... -f`) — so every PID this spike measures or kills is the one captured at that mount's own launch, never found by scanning for a name or pattern.

**Ordering — both directions tested, not just asserted.** Mounting a share *before* its catch-all is up (a disposable `shadow-test` share, mounted directly on the plain pre-catch-all directory) succeeds and accepts writes, but the moment the catch-all is mounted over its parent, the share's own mount becomes **silently unreachable** — `ls` on the same path shows the catch-all's own (real, but empty) view of that directory instead, because the child mount is attached to a dentry inside the now-covered pre-catch-all tree. The orphaned process stays alive and stays listed in `/proc/self/mountinfo` throughout (confirmed, not assumed); unmounting the catch-all again re-exposes the child mount and its marker file reappears byte-identical — standard Linux mount-stacking behaviour, and the concrete mechanism doc 02 §1's `RequiresMountsFor=` requirement exists to prevent: a share started too early doesn't fail loudly, it silently stops doing what it's configured to do. The other direction is enforced by the kernel on its own: with all twelve shares mounted, unmounting the catch-all fails with `Device or resource busy`, and nothing is torn down by the attempt. Systemd's own boot-time ordering itself is not exercised — no init system in this container (doc 06 §3) — deferred to L3, which does not exist yet; this run establishes the mechanism the ordering exists to prevent, not the ordering enforcement itself.

**`mspmfs`/`epmfs` fallback**, on a dedicated three-disk array (separate from the standing lab array), both pools over the identical branches, differing in exactly `category.create`:

| Case | Result |
|---|---|
| Baseline (positive control): `media` exists only on `mfp1`, not yet full | Write lands on `mfp1` |
| `mfp1` filled below `minfreespace` (50M) via `fallocate`, real free space remains | `df` confirms 224,575,488 B → 20,971,520 B free |
| `epmfs`, `media` still exists only on the filtered `mfp1` | `No space left on device`, exit 1 |
| `mspmfs`, identical branches and fill state | Succeeds, lands on `mfp3` — confirmed absent from `mfp1`/`mfp2` |

man/mergerfs.1's `epmfs` entry ("Of all the branches on which the relative path exists choose the branch with the most free space") and `mspmfs` entry ("Like epmfs but if it fails to find a branch it will try again with the parent directory. Continues this pattern till finding one.") both match the observed behaviour exactly. **Q11's `mspmfs` default is confirmed as designed, not reverted.** A test-design bug was found and fixed while writing this: an earlier version ran `mspmfs` before `epmfs`, and `mspmfs`'s own fallback write created `media/` on `mfp3` as a side effect of sharing branches with the `epmfs` pool — which then let `epmfs`'s write succeed too, an artifact of test ordering, not of `epmfs`'s own behaviour. Fixed by running `epmfs` first, while `media` still exists on exactly one (filtered) branch.

**`NC` branches**, against a cache-then-move share: a file written directly to an `NC` (array) branch reads back byte-identical through the share; five new files written through the share all land on cache, none on any `NC` branch (man/mergerfs.1: "NC: (no-create) - Will be excluded from create policies"); appending to and deleting the existing file through the share both succeed, changing/removing it on the `NC` branch directly (man/mergerfs.1's own next clause: "You can't create on that branch but you can change or delete") — every one of these confirmed against the real branch, not the pool's own view.

**Catch-all**: a write to a brand-new top-level path with no per-share mount of its own lands on a data disk (never cache, never outside the pool) through the catch-all's own default policy — confirmed by locating the file on the real branch, not just observing the write succeeded.

**Cost.** No page-cache-dropping mechanism is available in this container — checked directly, not assumed from S1: `/proc/sys` is itself bind-mounted `ro` (`mount | grep proc/sys`), so `echo 1 > /proc/sys/vm/drop_caches` fails with `Read-only file system` even though the file's own permission bits would otherwise allow it. `dd ... iflag=direct` bypassed the page cache on the read side instead. RSS per share: 7,004–9,136 KiB (a spread, not one number); twelve shares total 88,812 KiB (≈87 MiB); the full 14-process topology (+ catch-all + mover target) totals 105,828 KiB (≈103 MiB) — well under R12's 200 MiB "too high" bar.

Sequential-read throughput needed a second pass: an earlier attempt at this step ran every twelve-shares rep before any single-mount rep and attributed a depressed first twelve-shares rep to mount count, which an independent verifier reproduced as a run-order artifact, not a mount-count one — reversing which scenario ran first moved the depression to the other scenario. The corrected design counterbalances scenario order (an ABBA pattern: pair 1 single-mount-then-twelve-shares, pair 2 the reverse, and so on, so each scenario's mean position in the run is nearly identical) and takes four discarded warm-up reads in each state before counting begins — one warm-up wasn't enough; the climb spans several repetitions after each mount/unmount transition, not just the first read, a design arrived at by iterating in the lab (single generic warm-up, then one warm-up per state, then four) until a fresh run's own warm-up log stopped showing a residual climb (`results/cost-throughput-warmup.log`). Five reps per scenario: single-mount 5.2766/5.2810/5.2821/5.3572/5.3449 GB/s (median 5.2821), twelve-shares 5.2903/5.4487/5.2673/5.1781/5.2826 GB/s (median 5.2826) — relative loss by median **−0.01%** (twelve-shares marginally faster, within noise), spreads overlapping almost entirely, comfortably under R12's 10% bar. An order-effect check (Pearson r between sequence position and throughput, pooled across scenarios) is reported either way, not just when it turns something up: this run's own value is **r = −0.090**, close to zero — named as a measurement caveat regardless, not explained away, because this one committed run cannot show whether a near-zero reading generalizes; a single run's near-zero r is not, by itself, stronger evidence than a single run's non-trivial r would be. Full data: `spikes/s6/README.md` §"Step 6 — Cost". Loop-device timings on a shared host, relative only, never product numbers (doc 06 §3).

**Failure.** Killing exactly `ao1`'s own mergerfs PID (confirmed against its own `/proc/<pid>/cmdline` immediately before the kill) leaves every operation against its mountpoint failing with `Transport endpoint is not connected` — `ls`, `stat`, `cat` all fail identically; `findmnt` still lists the stale mount; **the catch-all's own view of that path is never exposed as a fallback**, so a stray write during the outage has nowhere to land by accident. A plain `fusermount -u` on the dead mount succeeded on the first try (no lazy-unmount escalation needed), and a fresh remount reads the pre-kill data back byte-identical — the outage affects availability, never data.

**A container-environment finding, general, not specific to this spike's own claims**: a mergerfs process unmounted from a *different* script (process) than the one that started it becomes a permanent zombie in this lab container, because its PID 1 (`sleep infinity`) never reaps orphaned children. `kill -0` cannot distinguish this from a genuinely hung process (a zombie's PID stays valid until reaped); checking `/proc/<pid>/stat`'s state field does. 174 such zombie entries remained at the end of this run's full teardown (higher than an earlier run's 44, because the corrected Step 6 cost comparison mounts and unmounts the twelve shares many more times — the ABBA-counterbalanced design tears the topology down and rebuilds it repeatedly rather than once each way — more churn from the same fix, not a new kind of leak) — every one already cleanly unmounted, holding no memory or file descriptors, a property of this container having no init system rather than of mergerfs or of Hoserva's own future process supervision (which will always be a mount's direct parent). Recorded as a trap for any future lab-container test that checks process liveness with a plain `kill -0`.

**A `/src` finding**: `docker-compose.dev.yml` mounts the repository read-only (`.:/src:ro`) inside the lab container — writing spike results directly to a path under `/src` fails with `Read-only file system`. Results must be written under `$LAB` (the lab's own read-write bind mount) and copied out via `docker cp` (which preserves the calling host user's ownership, unlike files left inside `$LAB` itself, which stay root-owned per doc 08 S9's own finding) before `make lab-destroy`.

### Residual risk

- **Boot-time systemd ordering itself** (`RequiresMountsFor=` actually preventing the wrong-order mount from ever starting, rather than this spike's own scripted demonstration of what happens if it does) needs a real init system — L3, which does not exist yet.
- **Twelve mounts is this spike's own chosen scale**, matching the issue's acceptance criterion ("a dozen per-share mounts"); a real deployment with many more shares, or with much larger cache/array disks under real IO load (rather than loop devices backed by fast host storage), is not measured here.
- **The zombie-accumulation finding is a lab-container artifact**, not a claim about `hoservad`'s own process supervision, which this spike does not build or test.
- **The throughput comparison's order-effect check (above) is a real, unresolved measurement limitation of this lab**, not something the counterbalanced design eliminates outright — the one committed run's own relative-loss-by-median (−0.01%) is comfortably under the bar and its own order-effect r (−0.090) is close to zero, but a single run showing a near-zero r is not strong evidence the effect is gone for good, any more than a single run showing a larger one would be strong evidence it is repeatable; a future measurement on real hardware, with real IO contention rather than a shared dev host, and several more committed repetitions, is the way to close this rather than a larger warm-up in the same environment.

## Spike 7 — fanotify change journal

**Verdict: confirmed, agent-run in the lab, 2026-09-16, on every criterion the issue names.** A `FAN_MARK_FILESYSTEM` mark per data disk, distinct-`(dir-FID, name)`-pair counting, matches `snapraid diff`'s own changed-file total exactly for a workload covering every operation named (create, overwrite, append, delete, rename within and across directories, copy, touch — each both direct and through the mergerfs pool): **16 distinct paths from the journal, 16 changed files from `diff`**, side by side in `spikes/s7/results/run-all.log`. Queue overflow is both produced and correctly detected, with a same-size control proving the detection isn't a coincidence. A listener restart and a filesystem remount are both measured, not assumed, and both lose events silently — exactly the gap Q13's "approximate, unknown-until-next-sync" UI default already exists to cover. ext4 and single-device btrfs data disks behave identically to XFS; a btrfs subvolume mounted separately from its root fails to mark at all, with the exact error the issue's own upstream research predicted. Full scripts, the listener's source and one committed end-to-end run: `spikes/s7/`.

**Setup.** Loop-device lab (doc 06 §3), lab id `8-a1`, `make lab-up`'s own defaults (3×1 GiB data disks, 1 GiB parity, 512 MiB cache) — no override needed. `snapraid 12.4-1` (the same version S5 already validated in this lab), `e2fsprogs 1.47.2-3+b12`, `btrfs-progs 6.14-1` installed for this spike only (`spikes/s7/results/versions.log`). The listener (`spikes/s7/cmd/journal`) is a throwaway Go program using **only the standard library** — `golang.org/x/sys/unix`, which the issue's own proposed approach named, would touch the always-shared `go.mod`/`go.sum`, so this hand-declares the two syscalls (`fanotify_init`=300, `fanotify_mark`=301, the x86-64 numbers — amd64/linux only, stated plainly rather than generalised) and the on-wire structs from `linux/fanotify.h` directly. Built on the host inside the workspace (`CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build`) and run inside the container from the read-only `/src` bind mount.

**Identity, not a path.** This lab's container has `CAP_SYS_ADMIN` but not `CAP_DAC_READ_SEARCH`, so `open_by_handle_at(2)` — needed to resolve a fanotify file handle back to a real path — fails `EPERM` (established by spikes S1 and S6; confirmed to still hold here). The issue's own default ("distinct paths per disk") is therefore approximated by the nearest honest equivalent this lab can produce: **distinct `(directory-FID-bytes, reported-name)` pairs**, since the mark itself already scopes every event to one disk (one mark = one filesystem = one disk, confirmed unambiguous throughout this run — no cross-disk contamination was ever observed). This is stated as a difference, not hidden: the production daemon runs as root with `CAP_DAC_READ_SEARCH` and can resolve real paths, but that capability is **untested by this spike** — only the fallback identity scheme is confirmed to work.

**The comparison and why it holds.** `snapraid diff`'s own summary line categories (`added`/`removed`/`updated`/`copied`/`restored`, deliberately excluding `moved` — see below) sum to a "changed" total; the journal's distinct-`(fid,name)`-pair count across all three per-disk logs sums to a "journal" total. For the main workload (`spikes/s7/scripts/02-workload-compare.sh`) these were **16 and 16, exactly**, across create, overwrite, append, delete, same-directory rename, cross-directory rename, a timestamp-preserving copy, and both a metadata-only touch and a touch-of-a-new-file — half of these direct on a disk's own mountpoint, half through the mergerfs pool (`$LAB/mnt/user`). `moved` is excluded from the sum deliberately, not just left at zero by chance: **spike S5 already found this lab's SnapRAID can never classify a move as `moved` at all** (no data-disk UUIDs available, ever, in a container with no `udevd`) — every rename in this run's `diff` output shows up as a `remove`+`copy` pair instead, and the journal's own `RENAME_OLD`/`RENAME_NEW` pair for the same rename lands as two distinct `(fid,name)` entries for exactly the same reason: the *old* directory+name and the *new* directory+name are genuinely two different identities. The two mechanisms agreeing here is not a coincidence of this run's specific numbers; it follows directly from S5's own finding about this lab's move detection, stated once here rather than re-derived.

**Negative control (methodological, not part of the acceptance count): does the comparison actually notice a miss, or does it just agree when nothing is wrong?** `spikes/s7/scripts/03-negative-control.sh` starts a listener, makes two changes, stops it, then makes one more change with **no listener running at all**, then runs `diff`. The journal's own count (2, exactly the two changes it was running for) and `diff`'s count (3, correctly including the missed one) **do not match**, and the script asserts that they don't — proving the comparison mechanism can detect a real gap, not only report a coincidental match. This is the same shape of control S1's positive-control and S2's negative-controls sections already established as this project's standard (doc 08 §1, §2).

**Listener restart, measured (`04-restart-remount.sh`, part A).** A listener ran, saw one change, was stopped (`SIGTERM`, the same PID captured at launch); one further change was made with **no listener running**; a fresh listener instance started and saw one more change. Combined count across both instances: 2. `diff` for the whole window: 3. **The combined count undercounts by exactly the one file changed during the gap** — no error, no self-reported incompleteness, nothing distinguishes this from "only two things changed." This is precisely why Q13's UI default already says "approximate" and relies on the pre-sync `diff` for the exact number, and this run is the first time that gap has been measured with real numbers rather than assumed.

**Filesystem remount, measured (`04-restart-remount.sh`, part B).** A single, uninterrupted listener process (one PID throughout) saw a write before a disk was unmounted and remounted (`umount`/`mount` of the same loop device, same mountpoint), then a second write after. Distinct-path count: 1 before, **still 1 after** — the post-remount write was never captured, by the same still-running process, with no error, no exit, and no change in the process's own liveness. This matches the mechanism `fanotify(7)` and the kernel source describe: `FAN_MARK_FILESYSTEM` is scoped to a mounted filesystem instance (its superblock); unmounting destroys that instance, and a remount creates a new one the old mark was never attached to. **A production `hoservad` must re-arm each disk's mark after detecting a remount of that disk — a long-lived mark cannot be assumed to survive one.**

**Overflow, produced and detected, with a control (`05-overflow.sh`).** `fs.fanotify.max_queued_events` in this lab reads **16384** (`/proc/sys` is read-only here, so this was read, never lowered, per the issue's own constraint). A listener was started with `-delay`, deliberately not yet reading; **21,384** files (`max_queued_events` + a 5,000 margin) were then created directly on the marked disk (`xargs -n 1000 touch`, done in 0.3s — comfortably inside the 15s delay) while nothing drained the queue. The listener then read: **16,384 distinct paths captured (of 21,384 created), with an `OVERFLOW` marker present** — the queue filled and further events were genuinely dropped, exactly as `fanotify(7)` describes. A same-size **control** run with `FAN_UNLIMITED_QUEUE` set captured **all 21,384**, with **no** overflow marker — proving the drop in the first run is a real effect of the bounded queue, not an artifact of the burst, the listener, or the counting method. This is the concrete case Q13's design already names: **a production journal must treat an overflowed window as incomplete (the UI's "unknown until the next sync"), never present a partial distinct-path count as if it were exact** — this run shows the undercount is not a small rounding difference (16,384 vs 21,384 is a real, large gap) and that the `OVERFLOW` marker is exactly the signal needed to catch it.

**ext4 and single-device btrfs (Q23) (`06-ext4-btrfs.sh`).** A fixed four-operation workload (create, overwrite, delete, rename — against three baseline files plus one freshly-created one, chosen so no operation's target collides with another's, avoiding the distinct-count-collapsing edge case a create-then-immediately-rename-before-any-baseline would cause) was run against a 512 MiB ext4 image and, separately, a 512 MiB single-device btrfs image mounted at its own root (no subvolume) — the layout Q23 actually describes for a data disk. Both matched their expected count of 5 distinct paths **exactly**. `FAN_MARK_FILESYSTEM` behaves identically to XFS on both filesystems for every operation this spike exercises.

**The btrfs-subvolume EXDEV question, answered as measured.** A subvolume (`sub1`) was created inside the btrfs image and mounted **separately** from its root (`mount -o subvol=sub1`, a second, independent mountpoint for the same underlying device) — the case the issue's own upstream research named. `fanotify_mark(FAN_MARK_FILESYSTEM)` against that separate mount **failed**, with Go's `syscall.Errno` reporting exactly `invalid cross-device link` — **`EXDEV`**, confirming the issue's cited upstream research precisely, not just plausibly. The root-subvolume mount (above) needed no such handling and worked exactly like XFS/ext4. **Consequence for the config generator (doc 02 §2):** a data disk that is itself a plain, whole-device btrfs filesystem (mounted at its own root) needs exactly the same one `FAN_MARK_FILESYSTEM` call as an XFS or ext4 disk; a data disk laid out as a *subvolume distinct from its filesystem's root* would need its own mark per subvolume mountpoint, since one mark on the root does not cover it. Q23 already restricts v1 to XFS array disks with ext4/single-device-btrfs as a stated-but-unverified extension; this run adds that the change journal's own mechanism, specifically, already works for exactly the layout Q23 describes (whole-device, root-mounted) and would need explicit, separate handling only for a subvolume layout Q23 does not currently plan to support.

**One real implementation bug found and fixed while building the listener, general enough to be worth recording on its own:** a `fanotify_init` fd created without `FAN_NONBLOCK` is never treated by Go's `os.NewFile` as pollable, so calling `file.Close()` from a different goroutine (the signal handler, used to interrupt the listener for the restart test) does **not** interrupt an in-flight blocking `Read()` — confirmed directly: the listener stayed alive, non-zombie, 5 seconds after `SIGTERM` with the un-fixed binary. Adding `FAN_NONBLOCK` to the `fanotify_init` flags fixed it (Go's runtime then integrates the fd with its netpoller, and `Close()` correctly unblocks a pending read). Recorded in `spikes/s7/cmd/journal/main.go` and `spikes/s7/README.md`, since this would bite any future Go implementation of the real journal the same way.

**A SnapRAID behaviour this spike's own iteration tripped, not fanotify-specific:** re-running the workload script against an already-modified array (while debugging the bug above, before the fix) tripped SnapRAID's own built-in "all files previously present ... are now missing or have been rewritten" guard (`../reference/snapraid/cmdline/scan.c`: fires when `count_equal == 0` for a disk — not one single file on it stayed exactly unchanged). This is a genuine, separate safety mechanism from Hoserva's own threshold guard (doc 02 §2), and it fired correctly here because this spike's tiny fixture disks (2-5 tracked files each) had nearly all of their few files touched in one pass by design — a realistic workload against a realistic-size array would not come close to touching literally every file. Fixed by adding untouched filler files per disk (`spikes/s7/README.md`); recorded because it is real, general SnapRAID behaviour worth knowing, not a fanotify finding.

### Residual risk

- **Path resolution (`open_by_handle_at`) is untested by this spike.** This lab's container lacks `CAP_DAC_READ_SEARCH`; the production daemon runs as root and should have it, but that is assumed, not confirmed here. If it turns out to behave differently in production (e.g. a stale handle after heavy churn), the `(fid,name)` fallback this spike validates is the safe degradation path, not resolved paths.
- **Scale.** This run's workload touches on the order of ten to twenty files per disk; a real disk's fanotify behaviour under a much larger, sustained, realistic write rate (media ingest, a container's log driver) is not measured here.
- **GPT/real-disk UUID and multi-device btrfs are out of scope for this spike** (mirroring S5's own residual risk) — only loop-device XFS, ext4 and single-device btrfs were exercised.
- **L3 is needed to confirm the restart/remount findings survive a real init system and a real `hoservad` process supervisor** — this spike measures the raw kernel/fanotify mechanism, not any production re-arming logic that would compensate for it (which doesn't exist yet).
- **The overflow margin (max_queued_events + 5,000) is this run's own choice**, not derived from any specific real-world burst rate; a real disk under a genuinely pathological workload (e.g. a runaway process creating files in a tight loop) could produce a much larger or smaller gap than this run's 21,384-file burst.

| `mknod` of the NVMe's `b 259:0` and open it | `mknod` succeeds, `open` fails with *Operation not permitted* — the device cgroup rule is what blocks it |
| Host loop devices before / after | 0 / 0 — the per-image detach left nothing behind |
| AppArmor | Not present on this host, so this recipe cannot test it directly; confirmed required on hosted Ubuntu runners instead — see "Hosted CI runners" below |

**Two things the design had missed:**

1. **The lab leaves root-owned files in its bind mount.** Images and mount directories are created by root inside the container, so the unprivileged user cannot delete them afterwards (`rm: … Keine Berechtigung`). Teardown must remove `.lab/<id>` **from inside the container** before it exits — otherwise the orchestrator cannot delete an agent's scratch clone. Doc 06 §3 and the orchestrate skill now say so.
2. **Debian's mergerfs build reports `mergerfs vunknown`** for `--version`. `hoserva doctor` and version pinning must read the installed version from package metadata (`dpkg-query -W -f '${Version}' mergerfs`), never from the binary.

**Partial S8: both storage dependencies are in Debian 13.** `apt-cache policy` in `debian:trixie-slim`: `mergerfs 2.40.2-5`, `snapraid 12.4-1`. The assumption behind Q7 that SnapRAID might be unavailable is wrong; Q7's default is simplified accordingly. Still open at the time: whether 2.40.2 behaves as doc 02 needs (`mspmfs` fallback, branch modes — S6). **S8 is now fully answered — doc 08 §8, above** (option coverage, `-Z`/`-E` guard confirmation and the mergerfs/SnapRAID changelog review); this paragraph is kept as the historical record of what S9's own run established.

### Hosted CI runners (issue #10, 2026-09-16 — S9 closed)

**Verdict: CONFIRMED, all three questions.** Hosted GitHub runners support L2 (loop devices, FUSE, a real SnapRAID sync) and KVM acceleration for a single non-nested guest, and the lab's own `mount(2)` inside the container requires `apparmor=unconfined` on such a runner. **This closes S9.** S10 (nested KVM, VM-in-VM, issue #87, Phase 3.5) is a separate, still-open question — nothing here answers it. Full write-up, scripts and raw output: `spikes/s9/`.

**1. KVM: CONFIRMED.** Six consecutive hosted runs across this issue's fix attempts have booted a QEMU guest with KVM acceleration on a standard `ubuntu-24.04` hosted runner. Most recently, run `35076920766`, job `104731427908` (2026-09-16, head `e97c469`): `/dev/kvm` goes `crw-rw----` → `crw-rw-rw-` after GitHub's documented udev rule (reload, trigger, settle), the runner's own running kernel is acquired readably (`runner:runner 644`, via the runner's own job-scoped `sudo cp` + `chown`), and the guest boots with **QMP `query-kvm` replying `{"return": {"enabled": true, "present": true}}`**, followed by `## qemu-system-x86_64 exit 0, wall time 1s`. Acceleration is confirmed **host-side, by the QEMU process itself**, not only inferred from the guest's own `/proc/cpuinfo`. This closes S9's KVM acceptance criterion ("a QEMU guest boots with KVM acceleration on a standard hosted runner").

**2. Lab (L2): CONFIRMED.** The same run's `lab` job (`104731428284`) ran `lab-up`, `lab-seed`, `lab-verify-refusal` (the host-device refusal checks for the NVMe and SCSI/SATA device-cgroup classes, both correctly `EPERM`, plus `lab_assert_own_loop`'s own path checks, which refuse through `die()` and carry no errno at all), a SnapRAID sync against the standing array (`Everything OK`), and `lab-destroy` — all green, on the pinned `ubuntu-24.04` image, in the same run as the KVM confirmation above.

**3. AppArmor necessity: ANSWERED — `apparmor=unconfined` is REQUIRED.** Run `35076920766`, job `104731428284` (same run as above) ran the real lab recipe three times, on one runner, one image, under three distinct `HOSERVA_LAB_ID`s, differing only in the container's AppArmor profile:

| Time (UTC) | AppArmor profile | Lab id | Outcome |
|---|---|---|---|
| 09:00:43 | `unconfined` (control) | `…-apparmor-ctrl` | `lab … ready: parity1, disk1-3, cache, pool` |
| 09:00:55 | `docker-default` (variant) | `…-apparmor-var` | `mount: /lab/…/mnt/parity1: /dev/loop0 already mounted or mount point busy.` / `make: *** [Makefile:110: lab-up] Error 32` |
| 09:01:06 | `unconfined` (the job's own standing lab) | base id | `lab-up`, `lab-seed`, both EPERM refusal checks, SnapRAID `Everything OK`, `lab-destroy` |

**The A-B-A ordering is what makes this conclusive.** `unconfined` succeeded both immediately before and immediately after the `docker-default` failure — the second success landing one second after the failing variant's own teardown, on the same runner, against the same loop devices — which rules out leftover state, loop contention and an ordering artifact from inside this run itself as the cause of the middle failure.

The third arm (09:01:06) was **not designed as a control for this experiment** — it is the job's own standing lab run, which happens to supply the second `unconfined` success. It is reported here because it corroborates the two-arm result, not as a designed three-arm experiment.

The verdict step reads the variant arm's own recorded step outcome (`if [ "failure" = "success" ]`) directly, never re-classifying stderr text into a verdict.

**4. What remains open: the errno.** The variant's failure is **EBUSY** ("already mounted or mount point busy"), where a mount denied by AppArmor would conventionally surface as **EACCES**. It also arrives *after* `losetup --find --show`, `lab_assert_own_loop` and `mkfs.xfs -q -L parity1` all succeeded against the same `/dev/loop0` — only the `mount(2)` call itself failed. This is recorded as an open, unexplained observation, worth investigating if it ever matters — not as a resolved mechanism. The established claim is necessity (removing the flag breaks the real lab recipe at its first mount), not an explanation of the kernel's exact error code.

**5. Corroboration, not primary evidence.** Moby's `docker-default` AppArmor template (`moby/profiles`, `apparmor/template.go`) contains `umount,` and a plain `deny mount,` with no `audit deny` anywhere in the file — consistent with a silently denied mount under Docker's default profile. This is cited only as upstream corroboration of the shape of the result; the primary evidence for this verdict is the run above, not this template.

**6. The honest history: six voids, and one dead end.** The AppArmor question was voided six times before this result — runs `35049304081`, `35056076616`, `35057453620`, `35068617498`, `35071011877`, `35075054897`. Every void traced to a bug in a hand-rolled replica of the lab recipe, never to AppArmor itself: a missing `mknod` of the container's own loop nodes; an undersized probe image (below `mkfs.xfs`'s own ~300MB minimum); an EBUSY misread as a denial; a `set -e` abort that stopped a second probe from ever running; a stale result file that read as a success; and finally a correct-but-inconclusive EBUSY the earlier apparatus had no way to interpret past. The narrative below keeps the first two of these six in detail, since they also carry the (separately confirmed) KVM and lab-half history; the later four are summarized in `spikes/s9/README.md`.

**Two runs printed "apparmor=unconfined is required" from broken experiments, and both verdicts were retracted at the time** — run `35049304081`, where both branches failed identically from the missing-`mknod` bug, and run `35057453620`, where the probe misread an EBUSY as a denial. Neither failure had anything to do with AppArmor. **The new result does not retroactively validate either retracted verdict.** These are two separate facts: an earlier claim was unsupported and withdrawn; a later, independent, methodologically sound experiment has since established the same conclusion on its own evidence. The old claim is not evidence for the new one, and the new one does not un-retract the old one.

**A host-side kernel-audit capture (added in a later, now-retired attempt) was a dead end.** It captured the runner's kernel audit log looking for `apparmor="DENIED" … operation="mount"` records, and found 288 AppArmor records and zero denials. That result proved nothing: Docker's default profile denies `mount` with a plain `deny` rule, and in AppArmor a plain `deny` is **unaudited** — only `audit deny` produces a log record. That round rested on an unchecked premise (that a denial would show up in the audit log at all) and has since been retired along with the rest of the hand-rolled apparatus it belonged to.

**The lesson worth carrying forward.** Every one of the six voids came from reimplementing the lab recipe in order to test it — raw `docker run`, manual `mknod`/`losetup`/`mkfs.xfs`/`mount`, a stderr classifier, a host-side audit capture — instead of exercising the real recipe through `make lab-up`/`make lab-destroy`. This is exactly the mistake `CLAUDE.md`'s "orchestrate, never reimplement" rule warns against, applied to a test probe rather than to product code. The fix that finally produced a conclusive result was to stop building a replica and instead run the real `make` targets twice with exactly one variable (`docker-compose.dev.yml`'s own `security_opt`, via a second compose file, `scripts/devenv/docker-compose.apparmor-default.yml`). Any future spike that needs to test a property of an existing recipe should default to varying the real recipe's own inputs, not building a parallel one that approximates it.

**The maintainer triggered `s9-hosted-probe.yml` once**: run `35049304081` (`workflow_dispatch`, `main`, 2026-09-16, overall `conclusion: failure` — the `kvm` job failed, the `lab` job succeeded). Fetched read-only, never re-run by this spike (`gh run view 35049304081 --repo mdg-labs/hoserva --json jobs,conclusion,event,headBranch`, and both jobs' `--log`). Excerpts: `spikes/s9/results/ci-run-35049304081-lab-job.log`, `ci-run-35049304081-kvm-job.log`.

**The `lab` job succeeded on the pinned `ubuntu-24.04` (image `20260907.300.1`)** — closing the "ran on `ubuntu-latest`, not the pinned image" gap the first pass of this spike left open. `lab-up`/`lab-seed`/`lab-verify-refusal` succeeded exactly as the earlier push-triggered run (`34950031773`, `ci.yml`'s own `lab` job, excerpt: `ci-run-34950031773-lab-job.log`) already showed — mergerfs pool at `.../mnt/user`, both host-device-refusal checks passing with EPERM — and **the SnapRAID-sync step this issue added succeeded on a hosted runner for the first time**: `snapraid 12.4-1`, `sync` exit 0, `Everything OK`, the same `WARNING! UUID is unsupported` line S5 already explained. `lab-destroy` reported the lab destroyed. Both of the gaps the previous entry here named (no SnapRAID sync hosted; pinned vs. `ubuntu-latest`) are now closed for real, on a hosted runner, not only on the dev host.

**The AppArmor step's verdict from that run is retracted, not carried forward.** Its log shows both branches failing identically — `losetup: device node /dev/loop0 (7:0) is lost` — because the probe never `mknod`-ed the container's own loop nodes the way the real lab's `scripts/devenv/entrypoint.sh` does, and it still printed `without-unconfined: FAILED — apparmor=unconfined is required on this runner image` regardless. **A control that fails cannot support a conclusion about the thing being varied.** Whether `apparmor=unconfined` is actually necessary on a hosted Ubuntu runner remains exactly as open as before this run — the dev-host S9 finding (no AppArmor on CachyOS) still couldn't test it either, and this run's attempt to test it was void. The workflow's AppArmor step is fixed (loop nodes `mknod`-ed inline like the real lab, a fresh image per branch so a second `mkfs.xfs` doesn't refuse against an already-formatted one, and the with-unconfined branch now treated as this experiment's own control — if the control itself fails, the step aborts loudly instead of asserting a verdict) but has not yet run hosted.

**The `kvm` job failed before `qemu-system-x86_64` was ever invoked**, at `no readable kernel at /boot/vmlinuz-6.17.0-1022-azure — cannot boot a guest`. The KVM acceleration question was never actually tested. What the same log does establish: `/dev/kvm` exists, group `kvm`, and goes `crw-rw----` → `crw-rw-rw-` after GitHub's documented udev rule, reload, trigger, settle — the mechanism works on this runner image — and the CPU reports `svm` (4 vCPU, 15 GiB RAM). The failure's cause: `/boot/vmlinuz-6.17.0-1022-azure` is the runner's own real, currently-running kernel — present, but mode `0600` owned `root:root`, unreadable by the plain runner user. (A now-rejected attempt 2 tried installing a *fresh* kernel package instead of fixing the read; `linux-image-generic`'s own postinst leaves the same 0600 root:root permissions, so it would have failed identically, just later — verified independently against the identical package.)

**The kernel-acquisition fix, and how it was validated under the actual privilege boundary (attempt 3).** `spikes/s9/scripts/kvm-boot-check.sh` copies the *running* kernel out with `sudo cp` and `chown`s the copy to the calling user — the runner's own passwordless, job-scoped `sudo`, already proven to work earlier in the same job (the udev-rule step used it successfully in run `35049304081`). Validated, not assumed, before ever running hosted: `spikes/s9/results/kernel-acquisition-nonroot.log` reproduces the exact 0600-root:root/unprivileged-reader boundary in a disposable container and shows the read failing before the fix and succeeding after it, checked as the unprivileged user throughout — the test attempt 2 was rejected for skipping, since its own validation ran everything as root. Acceleration evidence does not rest solely on the guest's own `/proc/cpuinfo` self-report: `-accel kvm` (no `,tcg` fallback list) makes QEMU refuse to start at all if KVM is unavailable, and the script also queries the running QEMU process directly over QMP (`query-kvm`), asserting `{"enabled": true, "present": true}` from the host side. Optionally, and clearly labeled as proving nothing about acceleration, the boot/QMP mechanics were end-to-end validated under pure TCG emulation in a disposable container with no `/dev/kvm` mapped (`spikes/s9/results/tcg-plumbing-check.log`) — this caught a real bug (a `jq '// "missing"'` expression that misreported a genuine `enabled: false` as `"missing"`, since jq's `//` treats `false` the same as null), fixed and re-validated in the same run.

**Run `35056076616` (`workflow_dispatch`, `main` at `1388f83`, 2026-09-16, overall `conclusion: failure` — the `kvm` job succeeded, the `lab` job failed) confirmed the fix for real.** Fetched read-only, never re-run by this spike (`gh run view 35056076616 --repo mdg-labs/hoserva --json jobs,conclusion,event,headBranch`, and both jobs' `--log`). Excerpts: `spikes/s9/results/ci-run-35056076616-kvm-job.log`, `ci-run-35056076616-lab-job.log`. The `kvm` job, on the pinned `ubuntu-24.04` (image `20260907.300.1`, `nproc: 4`, Azure `eastus2`): kernel acquisition printed `## Kernel acquired: /boot/vmlinuz-6.17.0-1022-azure -> ... (runner:runner 644)` — no "no readable kernel" failure — and the guest booted with `## QMP query-kvm reply: {"return": {"enabled": true, "present": true}}` followed by `PASS: guest booted to its own init in 1s; ... KVM acceleration confirmed by the host (QMP), not only inferred from the guest`. **This is the actual hosted run the previous update to this section said was still needed — it is no longer open.**

**The same run's `lab` job failed at the AppArmor step, on two new, narrower bugs — neither an AppArmor result.** With the `mknod` fix from run `35049304081` confirmed working (`losetup` no longer failed), the control branch reached `mkfs.xfs` for the first time and exposed: (a) the probe images were `truncate -s 64M`, but `mkfs.xfs` refuses anything under ~300MB (`Filesystem must be larger than 300MB.`) — the control guard worked exactly as designed, voiding the verdict rather than asserting one; (b) with the AppArmor step failing, `lab-destroy` (`if: always()`) ran with `steps.lab.outputs.id` unset, because "Derive this run's lab id" sat after the AppArmor step — `lab-require-id` correctly refused the empty value, a second, unrelated failure on top of the first. Both fixed by this change: the images are now 512M (validated against xfsprogs directly, no loop device, in `spikes/s9/results/mkfs-xfs-size-check.log` — 256M still refuses, 300M is the first size that succeeds, 512M passes with margin, and matches the lab's own `LAB_CACHE_SIZE` convention), and the lab id is now derived before the AppArmor step so teardown always has one to work with. `lab-up`/`lab-seed`/`lab-verify-refusal`/the SnapRAID sync never ran in this run (the AppArmor step failed first); those results still stand on run `35049304081`, not this one. AppArmor necessity remains exactly as open as before — this run's void result is a second void result, not evidence either way.

## Net effect on the risk register

| Risk | Was | Now |
|---|---|---|
| R1 — spindown regression | **High**, potential kill criterion | **Medium.** Not Hoserva-specific; a property of union filesystems. Converts into a useful feature via wake attribution. Agent-run in the lab, 2026-09-15: zero array-disk IO across all 6 acceptance-matrix windows (above) — residual risk (firmware wakes, real clients, L3) unchanged |
| Migration viability | Assumed, unverified | **Confirmed** by independent professional practice, and agent-run in the lab, 2026-09-16: synthetic Unraid-layout disks adopted read-only by UUID and unioned with matching sha256 checksums, with no exceptions on the primary XFS path (residual risk: scale, GPT/>2TB, ext4/btrfs, VM fixtures — doc 08 §2) |
| S5 — dev-workflow fidelity | Assumed, unverified (doc 07 §1's own kill criterion: "if not, the entire dev workflow needs rethinking before any code is written") | **Confirmed, with one named structural gap.** Agent-run in the lab, 2026-09-16: sync/diff/scrub/fix/undelete/touch and whole-array reconstruction under single *and* dual parity all match `snapraid.txt` exactly, including a clean/corrupt/repair cycle with matching sha256 and two independent byte-for-byte manifest reconstructions. The one gap — SnapRAID cannot read any data disk's UUID in this lab at all, degrading move detection and leaving the `-U` disk-identity guard unexercised — is structural (no `udevd` in a non-privileged container) and named with its covering layer (L3), not a workaround (doc 08 §5) |
| R12 — per-share mount topology fails S6 | **Medium**, per-share cache modes and allocation shrink to the two-mount fallback if the spike failed | **Retired for the topology itself; the throughput half of its own cost bar carries a named residual measurement caveat, not a clean "no cost" claim.** Agent-run in the lab, 2026-09-16 (redone once more after an independent verifier found and fixed a run-order confound in the original throughput measurement): a catch-all plus a dozen per-share mounts (all three cache modes) mount and unmount cleanly in dependency order; `mspmfs` falls back to the parent path exactly as documented while `epmfs`, changed only in that option, returns ENOSPC on the identical branches and fill state; `NC` branches stay readable while new files land on cache; a stray top-level write lands on a data disk; the twelve-share RSS cost (≈87 MiB) is well inside this risk's own 200 MiB bar; a counterbalanced, warmed-up throughput comparison shows a relative loss by median of −0.01% (twelve-shares marginally faster, within noise) in this run, comfortably under the 10% bar, with an order-effect check (Pearson r = −0.090, close to zero this run) that the lab's shared dev host cannot use to rule the residual effect out for good — a single committed run's near-zero reading is not stronger evidence than a single run's non-trivial one would be (doc 08 §6, "Residual risk"); a killed share mount fails safely rather than exposing the array beneath it. The two-mount fallback is not adopted |

Neither S1 nor S2 kills the plan. The spindown finding actually improves it: "we tell you which process woke your disks" is rarely offered by NAS tooling today, and it addresses a long-standing frustration for anyone running a union-filesystem pool. S5 confirms the foundation the other spikes and every later Phase 1 issue depend on: the L2 harness's SnapRAID behaviour is trustworthy for what it's asked to test. S6 confirms the storage design's own mount topology holds on Debian 13's mergerfs, removing the last open question that could still have forced a redesign before any storage code is written. S7 closes the contradiction Q13 was carried as: a fanotify change journal counts changes as accurately as `snapraid diff` itself, on every filesystem Q23 plans to support, without polling anything — S1's own implication 5 (doc 08 §1) is resolved, not just proposed.
