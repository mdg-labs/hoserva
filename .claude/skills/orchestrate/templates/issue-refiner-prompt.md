## Why this matters

Issues that were thin or out of date have repeatedly produced features that
were built as a package but **never wired into the running product** — a
service with no `hoservad` caller, a job type never registered, a handler
field left nil so every call returns `501 not_configured`, a test script no
`make` target runs. The implementing agent treats the acceptance criteria as
the definition of done and stays inside the scope paths it is given. If the
issue does not say where the capability must be reachable from, and does
not put that entry-point file in scope, it will not be wired. **Closing that
gap is the most important thing you do.**

Much of the planned work around these issues **already exists** on `dev`.
The issue text may predate it. Check before you describe anything as "to
build".

## Facts about the project that older issue text may get wrong

- Branches: `dev` is the working branch, `main` is release-only (Q46). There
  is no `beta` branch any more.
- There is **no hardware tier** (D20): every test runs in the loop-device lab
  or an agent-started L3 VM. No "L4 box", no maintainer-run test, no homelab.
- Hoserva's app catalog is its own, written from each app's upstream
  documentation (D19). It never references, fetches or derives from the
  Unraid Community Applications repositories or feed.
- `api/openapi.yaml` is the whole API (D18); every UI/CLI capability is an
  operation there, and handlers implement the generated interfaces.
- The database schema lives in `internal/store/schema/schema.sql`; migrations
  are generated by `sqlite-migrate` (`make db-migration`), never hand-written.
- Long-running work is a job registered with the scheduler in
  `cmd/hoservad/main.go`; system-touching code sits behind an interface with
  a fake.

## For each issue, in order

1. **Read it fully** — body, every comment (comments override the body),
   its epic, sub-issues, blocked-by and blocking.
2. **Read the design** — every doc section it cites, plus the doc sections
   its area obviously depends on. Note the exact `doc NN §N`, `Dn`, `Qn`.
3. **Inventory what already exists on `dev`** for this issue's capability:
   - packages and types (`git grep`), API operations in `api/openapi.yaml`,
     handler fields and their wiring in `cmd/hoservad/main.go`, job types and
     their registration, CLI commands in `cmd/hoserva/`, web routes in
     `web/src/routes/`, mock handlers in `cmd/mockapi/`, `make` targets;
   - stubs: `not_configured`, `501`, `TODO`, `PlaceholderPage`,
     `test.fail()`, `t.Skip`, handlers returning fixed data;
   - closed issues that already delivered part of it
     (`gh issue list --state closed --search "<keywords>"`), and the commits
     behind them (`git log --grep '#<n>'`).
4. **Check staleness** — list every instance:
   - `beta`, "L4", hardware-tier or maintainer-test language, Community
     Applications references;
   - paths, types or commands that no longer exist or were renamed;
   - acceptance criteria already met on `dev` (cite file:line / commit);
   - doc 13 defaults the text contradicts;
   - references to issues that are closed, cancelled or merged elsewhere.
5. **Close missing scope.** Every `feat` or `bug` that delivers a runtime
   capability gets an acceptance criterion of the form
   `Reachable via: <entry point> → <capability>` — an API operation served
   by `hoservad` (not only the mock), a CLI command, a web route, a nightly
   chain step, or, for a test or check script, the `make` target and CI job
   that runs it. Name the entry-point files in the scope hint
   (`cmd/hoservad/main.go`, `cmd/hoserva/…`, `web/src/routes/…`,
   `Makefile`, `.github/workflows/…`). If the mock API gains or changes an
   operation, the matching `cmd/mockapi/` change is in scope and must mirror
   production validation.
6. **Name the adjacent work** under `## Out of scope`, with the issue number
   where each piece lives. Wiring is never "out of scope" unless a named,
   open issue owns it and this issue is blocked-by or blocking it.
7. **Estimate size** — changed lines excluding generated code (`api/gen/`,
   `internal/store/db/`, lockfiles). **This is a hard gate:** any issue
   whose realistic estimate exceeds ~800 lines is `split-proposed`, never
   `refined`. Split into parts that each ship on their own **and each carry
   their own wiring** (their own `Reachable via`) — vertical slices, never a
   "package" issue plus a later "wire it in" issue. No part above ~800.
   Before proposing a new part, check the other open issues and epics
   (`gh issue list --repo mdg-labs/hoserva --state open --search "…"`): if
   another open issue already owns that work, make this issue blocked-by it
   instead of duplicating it.
8. **Write the refined body** in this shape (github-triage's):
   - `## Original report` — the current body **verbatim**, plus any comment
     that changed scope, quoted with its date.
   - `## Summary` — one or two sentences on what this delivers, as of `dev`
     today.
   - `## Design references` — doc sections and `Dn`/`Qn`.
   - `## Current state on dev` — what exists already, what is a stub, with
     file:line or commit; "nothing yet" is a valid answer.
   - `## Proposed approach` — only where the design leaves a real choice.
   - `## Acceptance criteria` — checkable, complete; nothing beyond them is
     required. Includes `Reachable via: …`. Storage work names its lab test;
     `safety-critical` work names the data-loss scenario its test
     reproduces; UI work names the error and empty states it shows.
   - `## Out of scope` — adjacent work with issue numbers.
   - `## Open questions` — only if one remains; each with a recommended
     default (cite `Qn` where it exists).
   - `## Scope hint` — the top-level paths, in backticks, **including the
     entry-point files**, and the size estimate.
   Never express epic membership or dependencies as prose — report them in
   the verdict instead; the caller wires them natively. When the body
   refers to an issue you are proposing (a split part), write it as
   `<NEW-A>`, `<NEW-B>`, … and use the same labels in the verdict — the
   caller creates those issues and patches the numbers in. Never write "see
   verdict" in a body: the body is read by people who never see it.
